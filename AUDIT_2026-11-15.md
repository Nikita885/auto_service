# Аудит проекта — 15 ноября 2026

## Границы проверки

Проведён обзор исходников Django/API, авторизации, записи, уведомлений, интеграции 1С, клиентского веб-приложения, Android-оболочки, дизайн-токенов, конфигурации Docker/nginx/CI и состава тестов. Это статический аудит, а не полный пентест или подтверждение работы каждой функции. Код не исправлялся.

Запуск `python -m pytest -q` завершился до сбора тестов: в Python 3.12 нет pytest. Во втором доступном Python 3.14 pytest также отсутствует. Команды docker/node/uv не найдены через Get-Command. Сервер, Android-сборка, эмуляторы и реальные устройства не запускались. Заявленные README результаты тестов не считаются результатом этого аудита. Визуальные выводы относятся к системе оформления в исходниках; фактическое качество вёрстки на устройствах требует отдельного прогона.

## Общий вывод

Проект имеет хорошую основу: серверные бизнес-сервисы, транзакции и блокировки, ограничения доступа, тесты на PostgreSQL в CI, общий слой API, единые дизайн-токены. Но считать продукт полностью проверенным и готовым к массовому запуску пока нельзя: есть дефекты восстановления после ошибок, отзыва доступа и ограничения затрат подсказчика; есть пробелы в пользовательских сценариях и мобильной проверке.

Android — Java WebView-оболочка над `/app/`. iPhone — PWA, устанавливаемая на главный экран, отдельного нативного iOS-проекта в обозреваемой структуре нет. Единая страница обеспечивает общность оформления, но не гарантирует одинакового поведения WebView и Safari.

## Найденные проблемы

P1 — исправить перед расширением эксплуатации; P2 — запланировать ближайшим этапом. «Подтверждено по коду» означает наличие дефекта в логике; воспроизведение на устройстве отдельно не проводилось.

### 1. P1: сбой обновления токена стирает вход

**Подтверждено по коду.** `apps/web/static/web/js/core.js:93–95`: любой отказ refresh, включая сетевую ошибку или HTTP 502, вызывает `store.clear()`. После истечения access-токена кратковременная потеря связи уничтожает и действующий refresh. Затем `onSignedOut` очищает клиентский кеш.

Исправление: отзывать локальную сессию только при окончательном отказе авторизации; при сетевой ошибке/5xx сохранять токены и давать повторить запрос. Проверка: истёкший access + действующий refresh + отключение сети/502 при обновлении не должны требовать нового входа.

### 2. P1: лимиты подсказчика обходятся параллельными запросами

**Подтверждено по коду.** `apps/assistant/services/assistant.py:251–288`: счётчики и бюджет проверяются до запроса провайдеру, запись расхода сохраняется после него. Одновременные запросы могут пройти одну проверку до появления записей друг друга. `AssistantView` не задаёт отдельную throttle_scope. Неудачи провайдера исключены из дневного лимита, поэтому тоже требуют ограничения частоты.

Последствие: превышение дневного лимита, бюджета и занятость серверных обработчиков. Исправление: атомарно резервировать квоту и предполагаемую стоимость, ограничить число одновременных запросов пользователя и общий поток; освобождать резерв при отказах. Месячный бюджет должен учитывать запросы в работе.

### 3. P1: открытый WebSocket сохраняет устаревшие права

**Подтверждено по коду.** `apps/common/ws_auth.py`, `apps/master/consumers.py:24–60`, `apps/booking/consumers.py`: токен и пользователь проверяются при подключении, группы выбираются один раз; при передаче событий права не перепроверяются. Блокировка сотрудника, снятие роли или изменение точек не отключают уже открытую подписку. Истечение JWT само по себе также её не закрывает.

Исправление: отключать соединения при изменении доступа, ограничить срок подключения сроком access-токена, проверять актуальную область доступа при доставке чувствительных событий. Проверка: заблокированный мастер перестаёт получать новые клиентские данные без ручного закрытия вкладки.

### 4. P1: зависимость Django сильно отстаёт от исправлений безопасности

**Подтверждено:** `requirements/base.txt:1` фиксирует Django 5.1.4. После неё выпускались исправления безопасности; ветка 5.1 находится среди неподдерживаемых выпусков. Наличие уязвимой зависимости не доказывает эксплуатацию конкретного эндпоинта.

Обновить на поддерживаемую ветку, совместимую с окружением и библиотеками, прогнать миграции и регрессию на PostgreSQL. Добавить аудит транзитивных зависимостей в CI и регулярное обновление.

Источники: https://www.djangoproject.com/download/ ; https://www.djangoproject.com/weblog/2025/jan/14/security-releases/ .

### 5. P2: приглашение теряется при временной ошибке

**Подтверждено по коду.** `apps/web/static/web/app/main.js:151–160`: `invite.done()` выполняется и после сетевого отказа/5xx при `/referral/attach/`. Код удаляется из ожидающих и помечается обработанным, хотя сервер мог его не принять.

Исправление: завершать обработку после успеха или окончательного бизнес-отказа; временный отказ оставлять для повторной попытки. Учесть неопределённый исход: сервер мог успеть применить код до обрыва ответа.

### 6. P2: сервис-воркер кеширует страницу ошибки вместо приложения

**Подтверждено по коду.** `apps/web/templates/web/app_sw.js:44–49`: навигационный ответ сохраняется в SHELL без проверки `response.ok`, типа содержимого и подходящего конечного URL. HTTP 502 считается успешным завершением fetch и перезаписывает рабочий кеш. Следующий запуск без сети может показать сохранённую ошибку.

Исправление: кешировать только корректный HTML приложения; на 5xx использовать последний рабочий shell. Запись кеша привязать к жизненному циклу события через waitUntil. Проверка: рабочий запуск → 502 → отключение сети → запуск должен открывать приложение.

### 7. P2: выход не отзывает refresh на сервере

**Подтверждено по коду.** `core.js:124`, `apps/accounts/urls.py`: signOut очищает локальное хранилище, отдельного API выхода/blacklist нет. Ранее скопированный refresh продолжает работать после нажатия «Выйти». Ротация refresh включена, но локальный выход её не выполняет.

Добавить отзыв refresh на сервере, локальную очистку выполнять даже при недоступности сервера. Для сотрудников рассмотреть завершение всех сессий и просмотр активных устройств.

### 8. P2: вложенные окна одновременно реагируют на Escape

**Подтверждено по коду.** `apps/web/static/web/app/lib.js:376–385`: каждый Sheet подписывает document на Escape. При двух Sheet событие закрывает оба; проверка учитывает только `.modal-backdrop`, а не верхний Sheet. В компоненте также отсутствуют управление фокусом, его возврат, удержание Tab внутри диалога и inert для фона.

Исправление: общий стек окон, Escape только для верхнего, перенос/возврат фокуса и блокировка доступности фона. Проверить клавиатуру и VoiceOver/TalkBack. Наличие aria-modal само по себе не реализует эти функции.

### 9. P2: Android игнорирует системное увеличение текста

**Подтверждено:** `ShellActivity.java:118` задаёт `setTextZoom(100)`. Пользователь с увеличенным системным шрифтом не получает соответствующего увеличения интерфейса. Это снижает доступность.

Поддержать масштаб текста, убрать ограничения, вызывающие обрезание, проверить большие шрифты и длинные имена/названия услуг. Сходство скриншотов двух платформ не должно требовать фиксированного размера текста.

### 10. P2: ошибка адресов маскируется бесконечным скелетоном

**Подтверждено по коду.** `apps/web/static/web/app/profile.js`, PointsSheet: если `list.data` отсутствует, всегда рисуется скелетон; `list.error` не обрабатывается. При отказе API и отсутствии кеша экран выглядит как незавершившаяся загрузка.

Показывать LoadError с повтором, скелетон только во время загрузки; кешированные адреса помечать устаревшими.

## Риски безопасности и продукта, требующие отдельного решения

- **Android-мост:** `addJavascriptInterface` + общий флаг trusted проверяют основную страницу, но не происхождение каждого вызывающего фрейма. Это не доказанный взлом: чужой исполняемый фрейм сначала должен попасть в WebView. Усилить мост ограничением origin/главного фрейма и запретом чужих фреймов; проверить postMessage API с допустимыми origin. Доступ к refresh через мост делает XSS особенно чувствительным.
- **Веб-токены:** на iPhone и в панелях refresh лежит в localStorage. Подтверждённой XSS в этом обзоре не обнаружено, но такой способ хранения увеличивает последствия XSS. Рассмотреть HttpOnly/Secure cookies с CSRF-защитой или серверную сессию; внедрять CSP после инвентаризации inline-скриптов и import maps. CSP в просмотренных настройках/шаблоне nginx не обнаружена; заголовки реального сервера не проверялись.
- **Мастер без точек видит все точки:** это явно описанное правило `User.service_points`, а не случайная ошибка проверки. Оно опасно при забытом назначении точки новому сотруднику. Предпочтительнее «нет назначений — нет доступа», а доступ ко всей сети задавать отдельным разрешением.
- **Приватность:** profile.js прямо отмечает отсутствие страницы политики; пользовательского удаления аккаунта в просмотренном профиле и auth API нет. Нужны политика, понятное информирование при регистрации и процедура удаления/обезличивания с учётом обязательных сроков хранения. Юридическое соответствие этим обзором не оценивалось.
- **Установка до первого действия:** gate() блокирует обычный браузер на Android и требует установку на iPhone при штатной конфигурации. Это намеренное решение, но оно создаёт лишний барьер для первой записи. Оценить разрешение браузерного сценария с предложением установки после успешной записи.
- **Пятиминутный черновик:** много шагов, ввод автомобиля и разговор с подсказчиком могут не укладываться в таймер. Проверить возможность продления при активности и сохранения введённых данных; измерять отказы на каждом шаге. Это UX-рекомендация, а не установленный сбой сервера.
- **Развёртывание:** prod compose монтирует исходники с хоста поверх образа. В результате собранный образ не гарантирует версию выполняемого кода. Лучше неизменяемый образ и отдельные writable-тома для данных, health checks и понятный откат.
- **SMS:** deliver_sms не проверяет, что Notification уже отправлено. При повторной доставке задачи после потери подтверждения возможна повторная SMS; окончательную гарантию нужно строить с идемпотентным ключом провайдера и учётом неопределённого результата отправки. Фактическое поведение провайдера в этом обзоре не проверялось.
- **CI:** в единственном найденном workflow есть Python lint/check/migrations/pytest, но нет Android build/lint/test, браузерных E2E, визуальной регрессии и dependency audit. Проверки Python не подтверждают работоспособность мобильной оболочки.

## Дизайн и единообразие

По исходникам стиль выдержан на уровне системы: design/tokens.json служит общим источником цветов, типографики, отступов, скруглений, анимаций и Android-ресурсов; есть тест синхронизации. Тёмная синяя палитра, неоновый акцент, общие иконки, карточки, Sheet, состояния загрузки и ошибок дают цельную основу. Полный редизайн без визуальной проверки не обоснован.

Что улучшать точечно:

1. Проверить иерархию на реальных экранах: одна явная главная кнопка, свечение на важном действии, спокойнее второстепенные элементы. Это направление проверки, не утверждение, что текущие экраны перегружены.
2. Проверить вспомогательный текст 12–13 px, контраст на всех фонах, большие системные шрифты, длинные названия и пустые состояния. Автоматически измерить контраст, не оценивать его только глазами.
3. Унифицировать обработку ошибок: при загрузке адресов уже есть расхождение с остальными экранами. Нужны стандартные состояния «загрузка / пусто / ошибка / устаревшие данные» для каждого блока.
4. Улучшить доступность модальных окон и системного размера текста. Это более обоснованный приоритет, чем косметическая смена палитры.
5. Проверить лендинг, панели и приложение серией скриншотов: 320/360/390/430 px и планшет/десктоп; после этого оценивать композицию, плотность, выравнивание и характер бренда.

## Что сделано хорошо

- Явные роли клиента/мастера/администратора и фильтрация клиентских объектов по владельцу.
- Централизация переходов статусов, история изменений и снимки состава/цен записи.
- Транзакции, select_for_update и ограничения БД в критичной бизнес-логике.
- Ротация refresh с blacklist, проверка активности пользователя при JWT-аутентификации WebSocket на подключении.
- В prod запрещён публичный ключ подписи, отключена общая выдача OTP в API, включены HTTPS/HSTS/secure cookies.
- БД и Redis закрываются от внешних портов в prod compose; контейнер запускается без root.
- Ключ 1С отделён от JWT сотрудников, сравнивается через compare_digest.
- Android ограничивает адрес оболочки, запрещает файловый доступ, включает отладку WebView только в debug; токены хранятся через Keystore.
- Общие компоненты, дизайн-токены, safe-area, уменьшение анимации, ленивый QR-декодер, явное отображение офлайн-данных.
- CI использует PostgreSQL, проверяет миграции, имеются тесты разных бизнес-сценариев.

## Обязательная матрица дальнейшей проверки

Android: минимальная поддерживаемая версия и актуальные устройства; старая/новая WebView; кнопка и жест «Назад»; возврат из звонка/карт; отказ/отзыв разрешения камеры; поворот; уничтожение процесса; повторное открытие App Link; крупный шрифт; клавиатура и системные отступы.

iPhone: Safari и установленная PWA; установка по приглашению; небольшой экран и экран с вырезом; клавиатура в формах и нижних окнах; камера/буфер/поделиться; возврат из фона; обновление service worker при открытом старом клиенте; истечение access без сети.

API/данные: параллельное бронирование последнего места; одновременная отмена/завершение; повторные подтверждения; конкурентное списание баллов; повтор задач и обмена 1С; часовой пояс точки, ночь и границы рабочего дня; изменение роли при открытом WebSocket. Наличие тестов в репозитории не заменяет их запуск на текущем состоянии.

Эксплуатация: запуск security_audit внутри prod-контейнера, проверка фактических TLS/заголовков/портов и OTP_DEBUG_PHONES без публикации секретов; восстановление БД и файлов из резервной копии; наблюдаемость очередей, ошибок SMS, интеграции 1С и затрат подсказчика; нагрузочный прогон с заранее определёнными целевыми задержками и числом одновременных пользователей. Выдерживаемая нагрузка сейчас неизвестна.

## Порядок работ

1. Исправить P1: refresh, квоты подсказчика, отзыв WebSocket-доступа, обновление зависимостей.
2. Исправить потери приглашения и рабочего offline-shell, серверный выход, ошибки адресов.
3. Исправить стек окон и доступность текста, подготовить страницы приватности и жизненный цикл аккаунта.
4. Сделать воспроизводимое окружение тестирования и добавить Android/browser проверки в CI.
5. Пройти матрицу устройств и визуальный аудит; затем принимать решения о точечных изменениях дизайна.
6. Проверить восстановление и нагрузку перед расширением эксплуатации.
