## 1. Что за проект

Backend-платформа для сети автосервисов с **одной услугой — замена масла**.
API обслуживает два мобильных приложения:

- приложение клиента — написано, Android на Java, лежит в `mobile/android`;
- отдельное приложение мастера (вторая версия, ещё не написана).

**Сайт записью не занимается.** В вебе есть лендинг (о компании, ассортимент
расходных материалов, адреса, ссылки на App Store и Google Play, телефон для
записи по звонку; цены по умолчанию скрыты), рабочее место
мастера с обновлением записей в реальном времени и панель администратора
с метриками. Клиент записывается в приложении или по телефону.

Репозиторий: https://github.com/Nikita885/auto_service
**Развёрнут и работает:** https://moiservis.pro (см. раздел 13).

## 3. Бизнес-требования (исходные)

1. Клиент регистрируется/входит **по номеру телефона без пароля**, через SMS-код.
2. Записывается в четыре шага: **адрес (их 2) → масло из наличия → свободное
   время → подтверждение**.
3. **Как только клиент начал записываться, создаётся объект состояния**, по
   которому в реальном времени видно, на каком он шаге и что уже выбрал.
4. На всю процедуру у клиента **5 минут** с момента начала. Не успел — запись
   удаляется, начинать заново.
5. Клиент может **отменить свою бронь**.
6. **Приложение мастера**: видит записи, имя клиента и выбранное масло, может
   удалить/отменить запись с последующим уведомлением клиента.

Серверная часть **готова полностью**, поверх неё работают лендинг и панели
сотрудников. 133 теста зелёные, ruff чистый, OpenAPI генерируется без

### Реализовано

- Вход по телефону + SMS-код, без пароля. Нормализация телефона в E.164.
  Код хранится только хешем. Лимиты: пауза 60 сек между отправками, 5 кодов на
  номер в час, 5 попыток ввода, TTL кода 5 минут.
- Пошаговая запись с черновиком на 5 минут и удержанием слота и канистры масла.
- Статус в реальном времени через WebSocket + REST-эндпоинт как запасной вариант.
- Отмена брони клиентом (не позже чем за час до визита).
- API приложения мастера: список записей, фильтры, поиск, отмена с обязательной
  причиной и автоматическим SMS клиенту, статусы работы, сводка за день,
  список записывающихся прямо сейчас.
- Склад масла с резервированием и списанием при завершении работ.
- Журнал уведомлений, SMS через Celery, абстракция SMS-провайдера. Боевой

  Постоянные отказы шлюза (`SmsRejectedError`) не ретраятся, временные

  уведомлений, за которые платить не хочется, — они остаются в журнале

- Метрики администратора: выручка, средний чек, доли отмен и неявок, воронка
  записи, динамика по дням, загрузка по часам, точки, ходовые масла, склад,

- Django-админка, healthcheck, демо-данные при первом старте.
- Веб на чистых HTML/CSS/JS: лендинг `/` (работает без JavaScript, цены и адреса

  `templates/web/_logo.html`, движение — в `static/web/js/landing.js`. Витрина

  в панелях сотрудников. Цены на сайте показываются только при

- Клиентское приложение под Android (`mobile/android`): Java, MVVM, вход по SMS,

- Реферальная программа: принудительная матрица 2×3 со спиловером. Под

- Эксплуатационная обвязка: `manage.py security_audit` проверяет чек-лист

## 6. Архитектурные правила — их важно соблюдать

1. **Вьюхи тонкие.** View разбирает вход сериализатором, зовёт функцию из
   `services/`, отдаёт результат. Бизнес-`if`-ов во вьюхах нет ни одного.
2. **Бизнес-логика только в `services/`.** ORM-запросы на запись за пределами
   сервисного слоя — повод развернуть ревью.
3. **Сервисы не знают про HTTP.** Они бросают доменные исключения из
   `apps/common/exceptions.py` (`ConflictError`, `GoneError`, `NotFoundError`,
   `ValidationError`, `RateLimitError`, `PermissionError_`). Превращение в
   HTTP-ответ — ровно в одном месте, `api_exception_handler`.
4. **Единый формат ошибки:**
   `{"error": {"code": "slot_taken", "message": "…", "details": {}}}`.
   Клиент разбирает машиночитаемый `code`, а не текст.
5. **Бизнес-параметры — в `settings.BOOKING` / `settings.OTP`**, читаются из `.env`.
   Никаких магических чисел в коде.
6. **Всё время в базе — UTC.** Локальное время берётся из `ServicePoint.timezone`.
7. **Переходы статусов записи — только через `_transition`** в
   `apps/booking/services/booking.py`: она проверяет допустимость, пишет историю
   и шлёт события.
8. **Уведомления и WebSocket-события — через `transaction.on_commit`**, чтобы не
   отправить SMS о записи, которая откатилась.
9. Комментарии в коде объясняют **почему**, а не что. Язык комментариев — русский.

## 7. Ключевые технические решения и их причины

- **Слоты не хранятся в БД.** Свободное время вычисляется на лету из графика точки
  (`slots.py`). Таблица слотов потребовала бы генерации вперёд, чистки и
  синхронизации при смене графика.
- **Черновик резервирует ресурсы.** Доступность =
  `ёмкость − активные брони − живые черновики`. Поэтому двое не выберут последнее
  время одновременно.
- **Таймер черновика не продлевается на шагах.** `expires_at` ставится один раз
  при создании. Иначе слот можно было бы удерживать бесконечно.
- **Истечение проверяется в трёх местах:** при чтении, на каждом шаге, и
  Celery-задачей раз в 20 сек. Черновик не «оживёт», даже если воркер лежит.
- **Проверки повторяются при подтверждении** — слот могли занять за время
  заполнения формы (`409 slot_taken`), масло могло кончиться (`409 oil_out_of_stock`).
- **Остаток масла не уменьшается при записи**, списывается ровно один раз при
  переводе в «Выполнена». Иначе пришлось бы возвращать канистру при каждой отмене.
- **В `Booking` продублированы имя, телефон, авто, название масла и цены** — это
  снимок на момент брони, чтобы история не поехала при изменении справочников.
- **API мастера — отдельное приложение**, а не флаг в клиентском API: у мастера
  другой набор полей (чужие персональные данные) и другие права.
- **`select_for_update(of=("self",))`** в `_lock_draft`: `select_related` по
  nullable FK даёт LEFT JOIN, а PostgreSQL не блокирует nullable-сторону внешнего
  соединения.
- **Блокировка строки точки** (`ServicePoint … FOR UPDATE`) при выборе времени и
  подтверждении — параллельные подтверждения выстраиваются в очередь.
- **Партиальные уникальные индексы:** `uniq_open_draft_per_user` (один живой
  черновик на клиента), `uniq_active_booking_per_user_slot` (нет дублей броней),
  `uniq_matrix_slot` (одно место в матрице — один человек, ловит гонку при
  одновременной регистрации), `uniq_accrual_per_booking_node` (одно начисление
  за запись, ловит повторное нажатие «выполнено»).
- **Рефералка — матрица, а не бинарка с меньшим плечом.** Замену делают раз в
  6–12 месяцев: слабое плечо наполняется месяцами, и схема, которая полгода не
  платит ничего, умирает. Матрица платит с первого визита приглашённого.
- **`sponsor` и `parent` в `ReferralNode` — разные поля.** Первый пригласил,
  под вторым человек оказался после спиловера. Начисления идут по `parent`.
- **В проде имена файлов статики с хешем** (`STORAGES` в `settings/prod.py`).
  HTML браузер не кеширует, CSS по неизменному адресу — кеширует надолго. Без
  хеша выкатка нового оформления давала бы вернувшемуся посетителю новую
  разметку со старыми стилями, и починить это задним числом нечем.
- **Обновление развёрнутого сервера — всегда с перезапуском `api`:** при
  `DEBUG=False` Django кеширует разобранные шаблоны в памяти процесса, а
  `collectstatic` запускается в `entrypoint.sh` при старте контейнера.
- **Длину линий знака меряет JS**, а не константа в CSS: знак перерисовывают,
  и прошитое число либо обрежет линию, либо оставит её мигать. Инструкция по
  замене рисунка — в README, раздел «Как подставить свой рисунок знака».
- **Фон витрины — цвет с фирменной картинки плюс генерируемая фактура.**
  `--void: #030b14` снят замером пикселей образца, облачность даёт
  `feTurbulence` в `data:`-URI, режим наложения `soft-light` (обычный
  обесцвечивал бы синеву в графит). Картинкой не сделано: вес, лишний
  запрос и видимый шов на широком экране.
- **Опасные переключатели прод не читает из `.env`.** `OTP_DEBUG_EXPOSE_CODE`
  в `settings/prod.py` всегда `False`, а `SECRET_KEY` из репозитория роняет
  запуск с `ImproperlyConfigured`. Опечатка в `.env` не должна стоить
  входа в любой аккаунт; всё, что можно проверить, не роняя работающий
  сайт (длина ключа, свежесть бэкапов), проверяет `security_audit`.
- **`NUM_PROXIES` задан явно.** По умолчанию DRF считает ключ throttling по
  всему `X-Forwarded-For`, а этот заголовок начинает писать сам клиент:
  лимит «10 кодов в час на IP» обходился сменой одной строки в запросе.
  Ошибка в другую сторону тоже опасна — при `0` за nginx у всех
  `REMOTE_ADDR` равен `127.0.0.1`, и лимит становится общим на весь сайт.
- **Текущий знак нарисован заливкой, а не обводкой** (`logo-lines-solid`):
  линия задана границами ленты, поэтому толщина переменная — для неона это
  выглядит лучше ровной обводки. Ценой того, что знак не прочерчивается, а
  загорается разом.

## 8. Модели

- **`User`** — UUID, `phone` (логин, E.164, уникальный), `full_name`, `role`
  (`client`/`master`/`admin`), `car_model`, `car_plate`, `service_points` (M2M —
  точки мастера, пусто = все). У клиента пароль unusable.
- **`OtpCode`** — `phone`, `code_hash`, `expires_at`, `used_at`, `attempts`, `request_ip`.
- **`ServicePoint`** — `name`, `address`, координаты, `timezone`, `opens_at`,
  `closes_at`, `workdays` (JSON, 0 = понедельник), `slot_minutes` (30),
  `posts_count` (сколько машин одновременно = ёмкость слота), `is_active`.
- **`Oil`** — бренд, название, вязкость, тип, объём канистры, `price`, `work_price`.
- **`OilStock`** — остаток масла на точке в канистрах, уникальная пара (точка, масло).
- **`BookingDraft`** — `user`, `step`, `is_open`, `close_reason`, `service_point`,
  `oil`, `slot_start`, `expires_at`, `booking`.
  Шаги: `started → point_selected → oil_selected → slot_selected → confirmed`,
  терминальные: `expired`, `cancelled`.
- **`Booking`** — `code` (короткий, вида `FRUQRE`), ссылки, `start_at`/`end_at`,
  `status`, снимок данных клиента и цен, `master`, `cancel_reason`, `cancelled_at`,
  `cancelled_by`, `reminder_sent_at`.
  Статусы: `pending`, `in_progress`, `completed`, `cancelled_by_client`,
  `cancelled_by_master`, `no_show`.
- **`BookingStatusLog`** — история смены статусов: кто, когда, комментарий.
- **`Notification`** — журнал SMS: получатель, тип, текст, статус, id у провайдера.
- **`ReferralNode`** — место клиента в матрице: `user`, `code` (код приглашения),
  `sponsor`, `parent`, `position` (left/right), `depth`, `balance` в баллах.
- **`PointsEntry`** — журнал движений баллов и источник правды по балансу: кому,
  сколько, за какую запись, с чьего чека, какой линией и по какой ставке
  (снимок — проценты меняются в `.env`, история нет).

## 9. API (базовый путь `/api/v1`)

**Аутентификация:** `POST /auth/otp/request/`, `POST /auth/otp/verify/`,
`POST /auth/token/refresh/`, `POST /auth/token/verify/`, `GET|PATCH /auth/me/`

**Справочники и доступность:** `GET /service-points/`,
`GET /service-points/{id}/oils/`, `GET /service-points/{id}/slots/?date=YYYY-MM-DD`

**Запись (черновик):** `POST /bookings/drafts/`, `GET /bookings/drafts/current/`,
`POST /bookings/drafts/{id}/select-point/`, `.../select-oil/`, `.../select-slot/`,
`.../confirm/`, `.../cancel/`

**Мои записи:** `GET /bookings/?scope=upcoming|history`, `GET /bookings/{id}/`,
`POST /bookings/{id}/cancel/`

**Мастер:** `GET /master/bookings/` (фильтры `date`, `status`, `service_point`,
`search`, `scope`), `GET /master/bookings/{id}/`, `POST .../cancel/` (причина
обязательна), `POST .../start/`, `POST .../complete/`, `POST .../no-show/`,
`GET /master/bookings/summary/?date=`, `GET /master/live-drafts/`

**Администратор:** `GET /master/metrics/?date_from=&date_to=&service_point=` —
сводная аналитика одним ответом (`totals`, `funnel`, `by_day`, `by_hour`,
`by_point`, `top_oils`, `clients`, `stock`, `live`). Только роль `admin`.

**WebSocket клиента:** `ws://host/ws/booking/?token=<access JWT>` — события
`draft.updated`, `draft.expired`, `draft.closed`, `booking.created`,
`booking.updated`, `booking.cancelled`. Payload совпадает с форматом REST.

**WebSocket сотрудника:** `ws://host/ws/master/?token=<access JWT>` — роль
`master`/`admin`, иначе закрытие с кодом 4403. Подписка на группы своих точек
`staff.point.<uuid>`, первым сообщением `master.ready` со списком точек. Дальше
идут **сигналы** (`booking_id`/`draft_id`, точка, код, статус, `local_time`), а не
состояние: мастерские сериализаторы живут в `apps.master`, тянуть их в
`apps.booking` — замкнуть зависимость, а персональные данные не должны улетать в
канал. Полные данные панель забирает REST-запросом со своими фильтрами.

## 13. Боевой сервер

Система развёрнута и работает. Это не план, а текущее состояние — при любых
правках учитывай, что они поедут на живой сервер.

**Где:** облачный сервер Timeweb (Ubuntu, 2 ГБ RAM), проект лежит в
`/opt/auto_service`. Docker и Compose поставлены из официального репозитория:
надстройке нужен Compose не ниже 2.24.

**Домены.** Основной — `moiservis.pro`. На него редиректят `301`:
`www.moiservis.pro`, `ekspres-zamena.ru`, `www.ekspres-zamena.ru` и
кириллический `экспрес-замена.рф` (в конфигах только как punycode
`xn----8sbarcksuknlkd6n.xn--p1ai`). Сертификат Let's Encrypt покрывает все
имена сразу, продление автоматическое.

**Запуск на проде — всегда с двумя файлами:**

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d
```

Базовый `docker-compose.yml` написан под разработку и пробрасывает наружу
5432, 6379 и 8000. На публичном адресе это Redis без пароля в открытом
интернете. Надстройка закрывает порты, оставляет `api` только на `127.0.0.1`
(снаружи ходят через nginx), собирает образ без dev-зависимостей и монтирует
статику в каталог хоста.

**Порты убираются тегами `!reset` / `!override`.** Списки Compose складывает,
а не заменяет: обычный `ports: []` оставил бы базовые проброшенными — молча,
без единой ошибки при запуске.

### Как обновляется сервер

```bash
cd /opt/auto_service && git pull
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
```

Именно `up -d`, а не `restart`: `env_file` перечитывается только при
пересоздании контейнера. При `DEBUG=False` Django держит разобранные шаблоны
в памяти процесса, а `collectstatic` выполняется в `entrypoint.sh` при старте —
поэтому правки шаблонов и статики без пересоздания `api` не видны.

`.env` и конфиг nginx на сервере правятся руками, в репозитории их нет.
Конфиг nginx на живом сервере уже содержит ssl-секции, дописанные certbot,
поэтому копировать `deploy/nginx.conf.example` поверх нельзя — изменения из
примера переносятся руками, дальше `nginx -t` и `systemctl reload nginx`.

После обновления и после правок `.env` чек-лист проверяется командой:

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml exec api python manage.py security_audit
```

Бэкапы снимает `deploy/backup.sh` на хосте по cron — он же чистит старые и
отправляет копию по `BACKUP_REMOTE`. Снимки лежат в `/opt/auto_service/backups`,
оттуда же их видит аудит.

### Что на проде отличается от разработки

- `DJANGO_SETTINGS_MODULE=config.settings.prod`, `DEBUG=False`.
- `BOOTSTRAP_DEMO=false` — иначе при каждом старте создавались бы демо-учётки
  с паролями из README, то есть открытая дверь в админку.
- `OTP_DEBUG_EXPOSE_CODE=False` — код входа не отдаётся в ответе API.
- `CSRF_TRUSTED_ORIGINS` заполнен. За HTTPS Django сверяет Origin форм с ним,
  а не с `ALLOWED_HOSTS`; без него вход в админку и панели отдаёт 403.
- Статика с хешами в именах, раздаёт её nginx, Django при `DEBUG=False` не
  отдаёт её вовсе.

### Грабли, на которые уже наступали

- **Кириллический домен приходит в `Host` как punycode.** В `ALLOWED_HOSTS`,
  `server_name` и у certbot нужна форма `xn--…`; с кириллицей Django отвечает
  `400` на каждый запрос.
- **`X-Forwarded-Proto` в nginx обязателен.** В проде включён
  `SECURE_SSL_REDIRECT`, схему Django берёт из `SECURE_PROXY_SSL_HEADER`. Без
  заголовка запрос считается пришедшим по HTTP, Django редиректит на HTTPS,
  nginx проксирует его обратно — петля редиректов.
- **Каталоги `static` и `media` на хосте принадлежат uid 1000** (пользователь
  `appuser` внутри контейнера), иначе `collectstatic` упирается в права.
- **В релизной сборке Android нужен основной домен, а не редиректящий.**
  Браузер `301` отработает, а OkHttp с JWT в заголовке — нет.
- **Регистратор подставляет свои A/AAAA на парковку.** При переносе домена их
  надо удалить: пока они живы, часть запросов уходит мимо сервера, а certbot
  не проходит проверку.

## 14. Задача: довести проект до промышленной зрелости

Проект **развёрнут и работает** на https://moiservis.pro. Любая твоя правка
через `git pull` поедет на живой сервер, которым пользуются. Это меняет цену
ошибки: сломанная миграция или упавший контейнер — это не «в следующий раз
поправим», а неработающий сайт и невозможность записаться.

### Сначала прочитай, потом трогай

В таком порядке:

1. `README.md` — полное описание системы, все решения и их причины.
2. Этот файл целиком, включая разделы 6 и 7 — правила и решения.
3. Код по слоям, снизу вверх:
   `apps/common/exceptions.py` → `apps/booking/models.py` →
   `apps/booking/services/` (там всё ядро) → `apps/master/` →
   `config/settings/base.py`.
4. Эксплуатацию: `docker-compose.prod.yml`, `docker/entrypoint.sh`,
   `deploy/nginx.conf.example`, раздел 13 этого файла.

**Документации не верь на слово.** Она пишется людьми и отстаёт от кода.
Прежде чем опереться на утверждение из README или отсюда — проверь его в
коде. Если нашёл расхождение, исправь документацию тем же коммитом.

### Чего делать нельзя

- **Складывать бизнес-логику во вьюхи.** Вьюха разбирает вход сериализатором,
  зовёт функцию из `services/` и отдаёт результат. Ни одного бизнес-`if`.
- **Делать ORM-запросы на запись вне сервисного слоя.**
- **Возвращать HTTP-ошибки из сервисов.** Сервис бросает доменное исключение
  из `apps/common/exceptions.py`; в HTTP его превращает ровно одно место.
- **Менять статус записи мимо `_transition`.**
- **Слать уведомления и события мимо `transaction.on_commit`** — иначе клиент
  получит SMS о записи, которая откатилась.
- **Добавлять зависимость, не обосновав.** В проекте нет ни одной лишней:
  каждая тянет вес образа, обновления и уязвимости. Если задача решается
  стандартной библиотекой в двадцать строк — решай ею.
- **Придумывать бизнес-правила.** Ставки, сроки, лимиты, тексты для клиента —
  спрашивай. Технические решения принимай сам.

### Планка качества

Работа не считается сделанной, пока не выполнено всё:

- `make test` зелёный. Сейчас 110 тестов — новых падений быть не должно.
- Новая логика покрыта тестами. Особенно граничные случаи: гонки, повторные
  нажатия, истёкшие сроки, права доступа.
- `make lint` чистый.
- `python manage.py makemigrations --check --dry-run` не находит изменений.
- Комментарии по-русски и объясняют **почему**, а не что. «Увеличиваем счётчик»
  не нужно; «читаем баланс под блокировкой, иначе два списания уведут в минус» —
  нужно.
- `README.md` и этот файл обновлены под изменения.
- Всё закоммичено осмысленным сообщением и отправлено в `main`.

### Что доделать, по приоритету

**1. Безопасность и эксплуатация — вперёд всего остального.**

Основное сделано, осталось довести на сервере. Что уже есть в коде:

- `manage.py security_audit` — чек-лист перед продом одной командой, с
  ненулевым кодом возврата. Запускать **на сервере**, внутри контейнера.
- `OTP_DEBUG_EXPOSE_CODE` в проде принудительно `False`, `SECRET_KEY` из
  репозитория роняет запуск.
- `deploy/backup.sh` — дамп PostgreSQL, ротация, проверка сигнатуры,
  необязательная копия по rsync. Восстановление описано в README.
- Лимиты по IP больше не обходятся подстановкой `X-Forwarded-For`
  (`NUM_PROXIES`); вход в Django-админку ограничен `limit_req` в nginx.
- Телефоны в логах маскируются, access-токен не попадает в access.log nginx.
- `restart: unless-stopped` у `db` и `redis` и ограничение размера логов
  Docker: после перезагрузки сервер поднимается сам, логи не съедают диск.

Что осталось:

- **Прогнать аудит на сервере и закрыть всё, что он покажет.**
- **Поставить `deploy/backup.sh` в cron и задать `BACKUP_REMOTE`.** Снимки на
  том же диске, что и база, от отказа диска не спасают. Восстановление
  обязательно проверить хотя бы раз.
- **152-ФЗ.** Телефоны и госномера — персональные данные: нужны политика
  обработки, согласие при регистрации (экран в приложении плюс страница на
  сайте) и подтверждение, что данные хранятся в РФ. Тексты и реквизиты
  оператора придумывать нельзя — это к заказчику.
- **Потолок расходов на SMS.** Лимиты на номер и на IP стоят, общего лимита
  на сутки нет: при массовом переборе номеров счёт растёт линейно. Нужна
  сумма, от которой плясать.

**2. Реферальная программа — внешняя часть.** Ядро написано и покрыто
тестами, но снаружи её не существует: у неё нет ни одного эндпоинта, клиент
не знает своего кода приглашения, мастер не может списать баллы, дерева и
журнала в панели администратора нет. Пока этого нет, дерево не вырастет, а
начисленные баллы некуда деть. Порядок: API → экран в приложении → списание
у мастера → дерево в панели.

**3. CI/CD.** Сейчас выкатка — руками по SSH. Минимум: GitHub Actions,
который на каждый push гоняет `ruff` и `pytest`. Дальше — автодеплой.

**4. Приложение мастера.** API и канал `ws/master/` под него готовы.

**5. Push-уведомления.** Поле `channel` в модели есть, отправки нет. Заодно
снимут часть расходов на SMS.

**6. Вторая услуга кроме замены масла.** Самое дорогое по последствиям:
`Oil` и `OilStock` заточены под канистры, понадобится сущность «услуга» и
миграция данных. Не берись за это раньше первых пяти пунктов.

### Как себя вести

- **Сначала прочитай, потом правь.** Половина ошибок в этом проекте была бы
  не сделана, если бы сперва посмотрели соседний файл.
- **Проверяй фактами, а не рассуждением.** Прогони тест, открой страницу,
  замерь, посмотри ответ сервера. «Должно работать» — не результат.
- **Если что-то не сделал или не смог — скажи прямо**, а не умолчи.
- **Не растекайся.** Просят одно — сделай одно и хорошо.
