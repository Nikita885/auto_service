# Автосервис — бэкенд записи на замену масла

Backend-платформа для сети автосервисов, оказывающих одну услугу — замену масла.
API обслуживает мобильные приложения — клиентское и приложение мастера.

Сайт записью не занимается: клиент записывается в приложении или по телефону.
В вебе живут лендинг с информацией о компании и ссылками на магазины приложений,
рабочее место мастера и панель администратора с метриками.

**Стек:** Django 5.1 · Django REST Framework · PostgreSQL 16 · Celery + Redis ·
JWT (simplejwt) · Django Channels (WebSocket) · Docker Compose

**Статус:** серверная часть готова и проверена — 110 тестов, линтер чистый,
сквозной сценарий прогнан по живому HTTP. В вебе работают лендинг и панели
сотрудников; записи у мастера обновляются в реальном времени. Клиентское
приложение под Android написано (`mobile/android`), приложение мастера — нет.

## Что умеет система

### Клиент

Записывается в мобильном приложении или звонком по телефону — на сайте формы
записи нет. Всё перечисленное ниже доступно через API, на котором работают
приложения.

1. Входит по номеру телефона — **пароля нет вообще**, только код из SMS.
2. Заполняет профиль: имя, марка автомобиля, госномер.
3. Записывается на замену масла в четыре шага: **адрес → масло → время → подтверждение**.
4. С момента нажатия «Записаться» у него **5 минут** на прохождение всех шагов.
   Не успел — черновик сгорает, начинать заново.
5. Видит статус процесса в реальном времени: на каком шаге, что уже выбрано,
   сколько секунд осталось.
6. Может отменить свою бронь (не позже чем за час до визита).
7. Получает SMS: подтверждение записи, напоминание за 2 часа, уведомление об отмене.

### Мастер (вторая версия приложения)

1. Видит список записей **в реальном времени**: новая запись, отмена и смена
   статуса появляются на экране сами, без перезагрузки.
2. В списке — время, код, **имя клиента, телефон, автомобиль, выбранное масло**.
3. Фильтрует по дате, статусу, точке; ищет по коду / имени / телефону / госномеру.
4. Ведёт запись по статусам: взять в работу → выполнено / клиент не приехал.
5. Отменяет запись с обязательной причиной — клиенту **автоматически** уходит SMS.
6. Видит, кто записывается прямо сейчас (незавершённые черновики).
7. Смотрит сводку за день: сколько записей, выполнено, отменено, выручка.

### Администратор

1. Всё, что доступно мастеру: смена, фильтры, действия по записям, живые черновики.
2. **Метрики по сети** за произвольный период: выручка с разбивкой на масло и работу,
   средний чек, доли выполненных, отменённых и неявок.
3. **Воронка записи** — на каком шаге клиенты отваливаются и сколько черновиков
   сгорело по таймеру.
4. Динамика по дням, загрузка по часам, сравнение точек, ходовые позиции масла,
   остатки склада с подсветкой заканчивающихся, приток клиентов.
5. Django-админка: точки, масла, остатки на складе, пользователи, записи, журнал SMS.

## Быстрый старт

```bash
git clone https://github.com/Nikita885/auto_service.git
cd auto_service
cp .env.example .env
docker compose build api && docker compose up -d
```

или просто `make up`.

> **Почему `build api`, а не просто `build`.** На машине разработчика проект лежит
> по пути с кириллицей (`…/Никита/Автосервис`), а `docker compose build` без имени
> сервиса падает: BuildKit не умеет не-ASCII в ключе сессии
> (`header key "x-docker-expose-session-sharedkey" contains value with
> non-printable ASCII characters`). Сервисы `worker` и `beat` используют тот же
> образ, что и `api`, поэтому одной сборки достаточно. Если склонировать репозиторий
> в путь без кириллицы — работает и обычный `docker compose up --build`.

Первый старт автоматически применит миграции и зальёт демо-данные: 2 адреса,
4 позиции масла, остатки на складе, учётки сотрудников.

| Что | Адрес |
|---|---|
| Лендинг | http://localhost:8000/ |
| Рабочее место мастера | http://localhost:8000/master/ |
| Панель администратора с метриками | http://localhost:8000/admin-panel/ |
| Swagger UI | http://localhost:8000/api/docs/ |
| ReDoc | http://localhost:8000/api/redoc/ |
| OpenAPI JSON | http://localhost:8000/api/schema/ |
| Django-админка | http://localhost:8000/admin/ |
| Healthcheck | http://localhost:8000/health/ |

**Демо-учётки** (создаются командой `bootstrap_demo`):

| Роль | Телефон | Пароль (только для админки) |
|---|---|---|
| Администратор | `+79000000000` | `admin12345` |
| Мастер | `+79000000001` | `master12345` |

В API оба заходят по SMS-коду, как обычные пользователи. Пароль нужен только для
входа в Django-админку.

**Как получить SMS-код в разработке.** При `OTP_DEBUG_EXPOSE_CODE=True` код
возвращается прямо в ответе `POST /api/v1/auth/otp/request/` в поле `debug_code`,
и дополнительно печатается в логи воркера (`docker compose logs worker`).
SMS-шлюз для разработки не нужен.

### Сервисы в Docker Compose

| Сервис | Что это |
|---|---|
| `api` | Daphne (ASGI) — HTTP + WebSocket, порт 8000 |
| `worker` | Celery worker — отправка SMS |
| `beat` | Celery beat — периодические задачи |
| `db` | PostgreSQL 16, порт 5432 |
| `redis` | Redis 7 — брокер Celery, кеш, channel layer |

`api`, `worker` и `beat` — это **один образ** с разной командой запуска
(YAML-якорь `x-app` в `docker-compose.yml`). Так гарантируется, что версия кода
в веб-процессе и в фоновых задачах не разъезжается.

### Правило слоёв

Это главное архитектурное решение проекта.

```
HTTP-запрос → View → Serializer (валидация формата) → Service (бизнес-логика) → ORM
```

**Вьюха** разбирает вход сериализатором, вызывает функцию из `services/` и отдаёт
результат. Бизнес-`if`-ов во вьюхах нет ни одного.

**Сервис** ничего не знает про HTTP. Он бросает доменные исключения
(`ConflictError`, `GoneError`, `NotFoundError`, …). Благодаря этому один и тот же
сценарий вызывается из HTTP-вьюхи, из Celery-задачи, из management-команды и из
тестов — без дублирования логики.

**Превращение исключения в HTTP-ответ** происходит ровно в одном месте —
`apps/common/exceptions.py::api_exception_handler`.

### Единый формат ошибки

Любая ошибка API выглядит одинаково:

```json
{
  "error": {
    "code": "slot_taken",
    "message": "Это время уже заняли",
    "details": {}
  }
}
```

Мобильный клиент разбирает машиночитаемый `code`, а не текст сообщения — тексты
можно править и переводить, не ломая приложения.

### Справочник кодов ошибок

| HTTP | `code` | Когда |
|---|---|---|
| 400 | `phone_invalid` | телефон не разобрался / некорректен |
| 400 | `otp_invalid` | неверный код, в `details.attempts_left` — остаток попыток |
| 400 | `otp_not_found` | код не запрашивали или он истёк |
| 400 | `draft_wrong_step` | шаг вне очереди; в `details` текущий и ожидаемый шаг |
| 400 | `draft_incomplete` | подтверждение при незаполненных параметрах |
| 400 | `slot_too_soon` | слот ближе минимального запаса |
| 400 | `slot_not_in_schedule` | такого слота нет в расписании точки |
| 400 | `slot_beyond_horizon` | дальше горизонта записи |
| 400 | `bad_date` | дата не в формате `YYYY-MM-DD` |
| 400 | `validation_error` | ошибка сериализатора; поля в `details.fields` |
| 403 | `permission_denied` | нет прав (клиент лезет в API мастера) |
| 403 | `point_not_allowed` | мастер обращается к чужой точке |
| 404 | `draft_not_found` / `booking_not_found` / `point_not_found` | объекта нет или он чужой |
| 404 | `oil_not_available` | масла нет на этой точке |
| 409 | `slot_taken` | время заняли, пока клиент думал |

| 409 | `duplicate_booking` | у клиента уже есть запись на это время |

## Модель данных

### `accounts.User`

Логин — телефон в формате E.164. Один пользователь на любую роль.

| Поле | Описание |
|---|---|
| `id` | UUID — публичные id не раскрывают количество клиентов |
| `phone` | уникальный, E.164 (`+79001234567`) |
| `full_name` | имя |
| `role` | `client` / `master` / `admin` |
| `car_model`, `car_plate` | автомобиль клиента — мастеру нужно знать, что заезжает |
| `service_points` | M2M: точки мастера. Пусто = доступ ко всем |
| `is_active`, `is_staff`, `date_joined` | стандартные |

У клиента пароль **unusable** — войти можно только по SMS. У мастера и админа
пароль есть, но только чтобы зайти в Django-админку.

### `accounts.OtpCode`

`phone`, `code_hash`, `expires_at`, `used_at`, `attempts`, `request_ip`.
**Сам код в базе не хранится — только хеш.** Утечка дампа не даёт войти в чужой аккаунт.

### `catalog.ServicePoint`

Адрес обслуживания. Сейчас их два, но модель это не ограничивает.

| Поле | Описание |
|---|---|
| `name`, `address`, `phone`, `latitude`, `longitude` | контакты и карта |
| `timezone` | часовой пояс точки, например `Europe/Moscow` |
| `opens_at`, `closes_at` | график работы |
| `workdays` | JSON-список дней недели (0 = понедельник); пусто = каждый день |
| `slot_minutes` | длительность слота, по умолчанию 30 |
| `posts_count` | **сколько машин обслуживается одновременно** = ёмкость слота |
| `is_active` | скрыть точку из выдачи |

### `catalog.Oil` и `catalog.OilStock`

`Oil`: бренд, название, вязкость (`5W-30`), тип (синтетика / полусинтетика /
минеральное), объём канистры, цена масла, стоимость работ, описание.

`OilStock`: остаток конкретного масла на конкретной точке, в канистрах.
Уникальная пара (точка, масло).

### `booking.BookingDraft`

Состояние процесса записи. Подробно — в следующем разделе.

### `booking.Booking`

| Группа полей | Что |
|---|---|
| `code` | короткий человекочитаемый код (`FRUQRE`) — клиент называет его на посту |
| `user`, `service_point`, `oil` | ссылки, `on_delete=PROTECT` |
| `start_at`, `end_at`, `status` | время и статус |
| `client_name`, `client_phone`, `car_model`, `car_plate` | **снимок** данных клиента |
| `oil_title`, `oil_price`, `work_price`, `total_price` | **снимок** позиции и цен |
| `master`, `client_comment`, `cancel_reason`, `cancelled_at`, `cancelled_by` | сопровождение |
| `reminder_sent_at` | защита от повторного напоминания |

**Зачем снимок.** Подорожает масло, клиент сменит машину или имя — история записи
не должна поехать. То, что было согласовано в момент брони, остаётся зафиксированным.

**Статусы:**

```
pending ──┬─→ in_progress ──┬─→ completed
          │                 └─→ cancelled_by_master
          ├─→ completed
          ├─→ cancelled_by_client
          ├─→ cancelled_by_master
          └─→ no_show
```

Разрешённые переходы описаны в `apps/booking/services/booking.py::ALLOWED_TRANSITIONS`.
Всё, чего там нет, — `409 invalid_transition`. Ни один переход не обходит функцию
`_transition`: она пишет историю и рассылает события, забыть её нельзя.

### `booking.BookingStatusLog`

Кто, когда и с каким комментарием менял статус. Нужен для разбора спорных ситуаций
и для аналитики (сколько отмен, сколько неявок).

### `notifications.Notification`

Журнал всех отправленных сообщений: получатель, тип, текст, статус доставки,
id у провайдера, ошибка. Нужен, чтобы доказать факт предупреждения об отмене,
не отправить одно и то же дважды и посчитать расходы на SMS.

### Два решения, которые стоит понимать

**Слоты не хранятся в базе.** Свободное время вычисляется на лету из графика точки
(`apps/booking/services/slots.py`). Таблица слотов потребовала бы генерации вперёд,
регулярной чистки и синхронизации при каждом изменении графика. Вычисление всегда
согласовано с настройками точки.

**Остаток масла не уменьшается при записи.** Доступность считается как
«физический остаток − активные брони − живые черновики». Списание происходит ровно
один раз — при переводе записи в «Выполнена». Иначе пришлось бы возвращать канистру
при каждой отмене и постоянно ловить рассинхрон.

## Ключевой механизм: черновик записи

Требование заказчика: **как только клиент начал записываться, в системе появляется
объект, по которому в реальном времени видно, на каком он шаге и что уже выбрал.
На всё про всё — 5 минут.**

Это реализовано моделью `BookingDraft`.

### Жизненный цикл

```
POST /bookings/drafts/          →  started            (создан, таймер пошёл)
    select-point                →  point_selected
    select-oil                  →  oil_selected
    select-slot                 →  slot_selected
    confirm                     →  confirmed          → создаётся Booking

в любой момент:
    cancel                      →  cancelled          (клиент прервал)
    таймер вышел                →  expired            (5 минут истекли)
    новый старт с restart=true  →  cancelled          (close_reason=restarted)
```

### Таймер не продлевается на шагах

`expires_at` ставится один раз, при создании: `now + 300 секунд`. Ни один шаг его
не двигает. Иначе слот можно было бы удерживать бесконечно, перещёлкивая масло
туда-сюда.

### Черновик резервирует ресурсы

**Пока черновик жив, он держит и слот, и канистру масла.**

```
свободных постов в слоте = posts_count − активные брони − живые черновики
доступно канистр масла   = остаток на складе − активные брони − живые черновики
```

Поэтому два клиента не выберут последнее свободное время одновременно. Отмена
черновика и истечение таймера освобождают резерв немедленно.

### Истечение проверяется в трёх местах

1. При чтении черновика (`get_open_draft`).
2. На каждом шаге (`_lock_draft`).
3. Celery-задачей `expire_stale_drafts` раз в 20 секунд.

Первые два гарантируют, что «протухший» черновик не оживёт, даже если воркер лежит.
Третье нужно, чтобы слот освободился для **других** клиентов, даже если владелец
черновика просто закрыл приложение.

### Проверки повторяются при подтверждении

Между выбором времени и нажатием «Подтвердить» может пройти четыре минуты. За это
время слот мог занять другой клиент (`409 slot_taken`) или масло могло закончиться
(`409 oil_out_of_stock`). Узнать об этом клиент должен **до** создания записи.

### Защита от гонок

- Строка черновика берётся под `SELECT … FOR UPDATE OF self` — шаги одного клиента
  сериализуются.
- При выборе времени и при подтверждении блокируется строка точки
  (`ServicePoint … FOR UPDATE`) — параллельные подтверждения на одну точку
  выстраиваются в очередь.
- Партиальный уникальный индекс `uniq_open_draft_per_user` — у клиента физически
  не может быть двух живых черновиков.
- Партиальный уникальный индекс `uniq_active_booking_per_user_slot` — один клиент
  не займёт один и тот же слот дважды.

> **Про `OF self`.** `select_for_update()` вместе с `select_related()` по nullable
> внешнему ключу порождает LEFT JOIN, а PostgreSQL отказывается блокировать
> nullable-сторону внешнего соединения (`FOR UPDATE cannot be applied to the
> nullable side of an outer join`). Поэтому блокируется только строка черновика —
> она и есть предмет гонки.

### Повторный старт идемпотентен

`POST /bookings/drafts/` при живом черновике **возвращает существующий**, а не
создаёт новый. Перезагрузка экрана не сбрасывает прогресс и не крадёт время
таймера. Чтобы начать заново намеренно — `{"restart": true}`.

## Аутентификация

Пароля у клиента нет. Вход только по одноразовому коду из SMS.

```
POST /api/v1/auth/otp/request/   {"phone": "+79001234567"}
     → {"phone", "expires_at", "resend_after_seconds", "debug_code"?}

POST /api/v1/auth/otp/verify/    {"phone": "+79001234567", "code": "4821"}
     → {"access", "refresh", "is_new_user", "user": {...}}
```

Если аккаунта с таким телефоном нет — он создаётся здесь же. Флаг `is_new_user`
подсказывает приложению, что стоит попросить имя.

### Нормализация телефона

`8 (900) 111-22-33`, `+7 900 111 22 33` и `79001112233` приводятся к одной строке
`+79001112233`. Без этого один человек завёл бы три аккаунта. Используется
библиотека `phonenumbers`, регион по умолчанию — `RU` (настройка `DEFAULT_PHONE_REGION`).

### Защита

| Уровень | Правило | Настройка |
|---|---|---|
| Пауза между отправками | 60 секунд | `OTP_RESEND_COOLDOWN_SECONDS` |
| Лимит на номер | 5 кодов в час | `OTP_MAX_PER_PHONE_PER_HOUR` |
| Попытки ввода | 5, потом код гасится | `OTP_MAX_VERIFY_ATTEMPTS` |
| Время жизни кода | 5 минут | `OTP_TTL_SECONDS` |
| Throttling по IP | DRF ScopedRateThrottle | `DEFAULT_THROTTLE_RATES` |

Новый запрос кода гасит предыдущий — рабочим остаётся только последний.
Код используется один раз (`used_at`), повторная проверка даёт ошибку.

### JWT

`access` живёт 60 минут, `refresh` — 30 дней, с ротацией и чёрным списком
(`ROTATE_REFRESH_TOKENS`, `BLACKLIST_AFTER_ROTATION`). Обновление —
`POST /api/v1/auth/token/refresh/`. Заголовок: `Authorization: Bearer <access>`.

### API мастера

Требует роль `master` или `admin`. Клиент получает `403`.

| Метод | Путь | Описание |
|---|---|---|
| GET | `/master/bookings/` | список записей |
| GET | `/master/bookings/{id}/` | детали + полная история статусов |
| POST | `/master/bookings/{id}/cancel/` | отменить: `{"reason": "..."}` — **обязательно** |
| POST | `/master/bookings/{id}/start/` | взять в работу |
| POST | `/master/bookings/{id}/complete/` | выполнено + списание канистры |
| POST | `/master/bookings/{id}/no-show/` | клиент не приехал |
| GET | `/master/bookings/summary/?date=` | сводка за день |
| GET | `/master/live-drafts/` | кто записывается прямо сейчас |
| GET | `/master/metrics/` | сводная аналитика — **только роль `admin`** |

Параметры списка: `date=YYYY-MM-DD`, `status=pending,in_progress`,
`service_point=<uuid>`, `search=` (код / имя / телефон / госномер), `scope=today`.

Мастер видит **полный телефон** клиента — ему нужно звонить, если тот опаздывает.
Именно поэтому API мастера вынесен в отдельное приложение со своими
сериализаторами, а не сделан флагом в клиентском API: смешивать их — верный способ
однажды отдать клиенту чужие персональные данные.

Если у мастера заполнено поле `service_points`, он видит только эти точки; попытка
тронуть чужую запись даёт `403 point_not_allowed`. Пусто = доступ ко всем точкам.
У роли `admin` ограничения нет.

### Метрики администратора

`GET /master/metrics/?date_from=YYYY-MM-DD&date_to=YYYY-MM-DD&service_point=<uuid>`

Мастеру этот эндпоинт закрыт: `403 permission_denied`. Выручка сети, воронка и
остатки — не то, что нужно человеку у подъёмника, поэтому права проверяет
отдельный `IsAdmin`, а не общий `IsMaster`.

Период по умолчанию — последние 30 дней. Сутки считаются в часовом поясе сети
(`BUSINESS_TIMEZONE`), а при фильтре по точке — в её собственном поясе.

Один ответ закрывает весь экран, чтобы панель не склеивала полдюжины запросов:

| Блок | Что внутри |
|---|---|
| `totals` | записи по статусам, выручка (масло + работа), средний чек, доли отмен и неявок |
| `funnel` | глубина черновиков по шагам, причины закрытия, конверсия в запись |
| `by_day` | динамика по дням; дни без записей приходят нулями, чтобы график не врал |
| `by_hour` | загрузка по часам суток |
| `by_point` | сравнение адресов по записям и выручке |
| `top_oils` | ходовые позиции масла |
| `clients` | всего клиентов, новые за период, возвращавшиеся |
| `stock` | остатки канистр с флагом `is_low` |
| `live` | живые черновики и предстоящие записи прямо сейчас |

**Глубина воронки считается по заполненным полям черновика, а не по его шагу.**
Шаг закрытого черновика перезаписывается на `expired`/`cancelled`, и информация
о том, докуда дошёл клиент, из него теряется. А `service_point`, `oil` и
`slot_start` остаются как есть — по ним и видно, где человек остановился.

Расчёт живёт в `apps/master/metrics.py`, вьюха только разбирает фильтры: правило
тонких вьюх действует и здесь.

## WebSocket

Каналов два, и устроены они по-разному.

```
ws://localhost:8000/ws/booking/?token=<access JWT>   клиент
ws://localhost:8000/ws/master/?token=<access JWT>    сотрудник
```

Токен передаётся в query-строке, потому что браузерный WebSocket не умеет слать
кастомные заголовки. Мобильные клиенты используют тот же контракт.

### Канал клиента

Личная группа `user.<uuid>`: приходит **полное состояние** — и тик черновика,
и смена статуса брони.

Сразу после подключения приходит снимок текущего состояния:

```json
{"event": "draft.updated", "payload": { …тот же формат, что в REST… }}
```

или `{"event": "draft.absent", "payload": null}`, если записи не начинали.

### События

| Событие | Когда |
|---|---|
| `draft.updated` | создан черновик или пройден шаг |
| `draft.expired` | вышли 5 минут |
| `draft.closed` | черновик подтверждён или прерван |
| `booking.created` | запись создана |
| `booking.updated` | сменился статус записи |
| `booking.cancelled` | запись отменена (клиентом или сервисом) |

Payload — **тот же формат, что у REST**. Клиент разбирает одну структуру
независимо от канала.

Канал односторонний; сервер отвечает только на `{"action": "ping"}` (чтобы держать
соединение).

REST-эндпоинт `/bookings/drafts/current/` остаётся полноценным запасным вариантом:
если WebSocket недоступен, приложение может опрашивать его раз в секунду.

### Канал сотрудника

Роль `master` или `admin`, иначе соединение закрывается с кодом `4403`. Сотрудник
подписывается на группы своих точек `staff.point.<uuid>` — те же точки, что видны
ему в REST (`accessible_point_ids`), иначе доступ и подписка разъехались бы.
Первым сообщением приходит `master.ready` со списком этих точек.

Дальше идут **сигналы**, а не состояние:

```json
{"event": "booking.created",
 "payload": {"booking_id": "…", "service_point_id": "…", "code": "FRUQRE",
             "status": "pending", "start_at": "2026-09-11T16:00:00+00:00",
             "local_time": "11.09.2026 19:00"}}
```

```json
{"event": "draft.updated",
 "payload": {"draft_id": "…", "service_point_id": "…", "is_open": true}}
```

Почему сигнал, а не готовая строка:

1. **Слои остаются чистыми.** Мастерские сериализаторы живут в `apps.master`,
   который зависит от `apps.booking`; тянуть их из `events.py` — замкнуть
   зависимость.
2. **На экране мастера фильтры** — дата, статус, точка, поиск. Вставлять
   пришедшую строку в список пришлось бы, повторив логику фильтрации на клиенте,
   а это верный способ однажды показать запись, которая под фильтр не подходит.
3. **Персональные данные не летят в канал.** Имя и телефон клиента мастер
   получает REST-запросом, где права проверяются на каждый вызов.

Панель по сигналу перечитывает текущую выборку. События приходят пачками
(закрытие черновика плюс создание записи), поэтому запрос делается один раз на
всплеск — с задержкой 400 мс.

Черновик без выбранной точки в канал не попадает: пока адрес не выбран, он не
относится ни к одному адресу.

Падение Redis не роняет бизнес-операцию — ошибки публикации только логируются.

## Реферальная программа

Клиент приводит знакомого по своему коду и получает баллы с его чеков.
Баллы — скидка на следующую замену, не деньги.

### Схема: принудительная матрица 2×3

Под каждым участником **два места** (`REFERRAL_WIDTH`). Начисления идут
**на три линии вверх** от того, кто заплатил, по ставкам
`REFERRAL_LEVEL_PERCENTS` — по умолчанию 5 %, 4 %, 3 %.

| Линия | Кто это | Ставка | Сколько людей максимум |
|---|---|---|---|
| 1 | кто стоит прямо над плательщиком | 5 % | 2 |
| 2 | над ним | 4 % | 4 |
| 3 | ещё выше | 3 % | 8 |

Полностью заполненная матрица — 14 человек под участником.

**Почему не классическая бинарка с выплатой за меньшее плечо.** Она платит
процент с оборота слабой ветки за период, и для этого нужен оборот в обеих
ветках. Замену масла делают раз в 6–12 месяцев: привёл троих, все попали в
левое плечо — правое пустое — выплата ноль, и так месяцами. Программа,
которая полгода не платит ничего, перестаёт работать раньше, чем участник
увидит первый балл. Матрица платит с первого же визита приглашённого.

**Спиловер.** Третий и следующие приглашённые не помещаются на первую линию
и падают ниже — в первое свободное место, обходом в ширину. Поэтому
`sponsor` (кто реально пригласил) и `parent` (под кем человек оказался в
матрице) — разные поля. Начисления идут по `parent`: иначе спиловер не имел
бы смысла. Побочный эффект полезный: тому, кто стоит под активным
спонсором, капает, даже если он сам никого не привёл, — при годовом цикле
визитов это единственное, что удерживает людей в программе.

### Сколько это стоит сервису

С каждого чека вверх уходит 5 + 4 + 3 = **12 %**. При чеке 6000 ₽ это
720 ₽. Если себестоимость замены 50 %, маржа с чека 3000 ₽ — значит
**программа съедает 24 % маржи**, каждый четвёртый рубль прибыли.

Это нормальная цена привлечения, если программа приводит новых клиентов.
Это чистый убыток, если ею пользуются те, кто пришёл бы и так.

**Считать процент лучше от работы, а не от полного чека**
(`REFERRAL_BASE=work`). Масло перепродаётся с почти фиксированной наценкой,
а чек скачет от 3000 до 9000 в зависимости от выбранной канистры: при
расчёте от полного чека дорогое масло увеличивает выплату, не увеличивая
заработок сервиса. По умолчанию стоит `total` — как в исходном расчёте
заказчика.

### Когда начисляем

Ровно в момент перехода записи в «Выполнена» — в
`booking.services.booking.complete()`, рядом со списанием канистры и
**внутри той же транзакции**. До этого деньги не получены, а запись можно
отменить. Внутри транзакции, а не в `on_commit`: баллы должны появиться
вместе с выполненной работой либо не появиться вовсе.

Импорт `apps.referral` в `apps.booking` сделан локально, внутри функции —
иначе приложения замкнулись бы друг на друга. Тот же приём уже используется
для уведомлений.

### Что защищено

- **Повторное начисление.** `complete()` нажимает человек, и нажать дважды
  проще, чем кажется. Частичный уникальный индекс
  `uniq_accrual_per_booking_node` не даёт начислить одному участнику за одну
  запись больше одного раза.
- **Гонка за место в матрице.** Два клиента могут регистрироваться
  одновременно и выбрать одно и то же свободное место. Ловит уникальный
  индекс `uniq_matrix_slot` на паре (родитель, место), после конфликта поиск
  повторяется.
- **Кольцо в дереве.** Спонсор из собственной ветки замкнул бы обход вверх,
  и начисление зациклилось бы. Проверяется до привязки.
- **Самоприглашение** и повторная привязка к другому спонсору.
- **Изменение ставок задним числом.** В каждом движении баллов лежит снимок
  применённой ставки и базы: проценты меняются в `.env`, история — нет.
- **Уход баланса в минус.** Списание читает баланс под блокировкой строки.
- **Бесплатная замена за баллы.** Потолок `REFERRAL_MAX_DISCOUNT_PERCENT`
  ограничивает, какую часть чека можно закрыть баллами.

### Модели

- **`ReferralNode`** — место клиента в матрице: `user`, `code` (код
  приглашения), `sponsor`, `parent`, `position` (left/right), `depth`,
  `balance`. `parent` удаляется через `PROTECT`: дерево — финансовая
  история, дырявить его нельзя.
- **`PointsEntry`** — журнал движений баллов и единственный источник правды:
  кому, сколько, за какую запись, с чьего чека, какой линией и по какой
  ставке. `ReferralNode.balance` денормализован и обновляется в той же
  транзакции — считать баланс суммой по журналу на каждый запрос дорого, а
  расходиться им нельзя.

### Настройки

```bash
REFERRAL_ENABLED=true
REFERRAL_LEVEL_PERCENTS=5,4,3   # длина списка задаёт и глубину
REFERRAL_BASE=total             # total | work
REFERRAL_WIDTH=2                # 2 = бинарная матрица
REFERRAL_MAX_DISCOUNT_PERCENT=50
```

### Чего ещё нет

Готово ядро: матрица, привязка по коду, начисления, списание, админка.
Снаружи программа пока не видна:

- клиент не видит свой код — нужен экран в приложении или SMS после первой
  замены, иначе приглашать нечем и дерево не вырастет;
- мастер не может списать баллы при расчёте — функция `points.spend()` есть,
  кнопки в панели нет;
- в панели администратора нет дерева и журнала — пока только Django-админка;
- бонус за меньшее плечо не реализован: его имеет смысл добавлять отдельным
  периодическим расчётом, когда наберётся оборот.

## Уведомления и SMS

| Событие | Текст |
|---|---|
| Код входа | `Код для входа: 4821. Никому его не сообщайте.` |
| Запись создана | адрес, время, масло, код записи |
| Напоминание | за 2 часа до визита |
| Отмена сервисом | с причиной, которую указал мастер |
| Работы выполнены | сумма |

Тексты собраны в одном месте — `apps/notifications/templates.py`. Формулировки
читает клиент, и правят их не программисты.

Отправка **всегда асинхронная**, через Celery: подтверждение записи не должно ждать
SMS-шлюз, а падение шлюза не должно откатывать бронь. Задача ставится в очередь
через `transaction.on_commit` — то есть только после того, как запись реально
попала в базу.

Все отправки логируются в `Notification`. **Текст кода входа в журнале
замаскирован** (`Код для входа: ****`) — сам код в базу не попадает.

### Подключение реального шлюза

`SMS_PROVIDER=console` (по умолчанию) печатает сообщения в лог воркера —
этого достаточно для разработки. Для боевой отправки подключён SMS.RU:

```bash
SMS_PROVIDER=smsru
SMS_API_KEY=<api_id из личного кабинета>
SMS_SENDER=<зарегистрированный буквенный отправитель>
```

**Бесплатной боевой отправки SMS не существует.** Бесплатны только тестовые
сообщения, которые шлюзы дарят при регистрации — их хватает, чтобы
проверить подключение, и не хватает ни на что больше. Всё остальное
оплачивается за сообщение.

Порядок подключения:

1. Зарегистрироваться на sms.ru, подтвердить свой номер.
2. Забрать `api_id` в личном кабинете (раздел «Программистам» → API).
3. Прописать его в `.env` на сервере и перезапустить контейнеры:
   `docker compose … up -d` (именно `up -d`, а не `restart` — `env_file`
   перечитывается только при пересоздании).
4. **Зарегистрировать буквенного отправителя** — https://sms.ru/?panel=senders
   Без него шлюз не пропускает ни одного сообщения и отвечает кодом 221.
   Это требование операторов, а не конкретного шлюза: отправка с общего
   номера в России закрыта, и сменой провайдера это не обходится. Имя
   должно соответствовать домену, названию юрлица или товарному знаку,
   проходит модерацию. Пока модерация не пройдена, отправки не будет
   вообще — планируйте этот шаг заранее.
   **Имя должно совпадать с доменом по написанию.** Основной домен —
   `moiservis.pro`, поэтому подавать стоит `MOISERVIS`.
   Прежние домены прошлого бренда (`ekspres-zamena.ru`, `экспрес-замена.рф`)
   формально тоже годятся как основание, но написаны с одной «с» и в SMS
   читаются как опечатка. `MOISERVIS` совпадает и с доменом, и с названием
   компании — подавать нужно его.
5. Прописать одобренное имя в `SMS_SENDER` и снова пересоздать контейнеры.
6. Проверить отправку, не проходя весь вход:
   ```bash
   docker compose … exec api python manage.py send_test_sms +79001234567
   ```
   Команда шлёт сообщение синхронно, мимо Celery, и печатает ответ шлюза
   целиком — ошибка ключа видна сразу, а не в логах воркера. На провайдере
   `console` она предупреждает, что сообщение никуда не ушло: «Отправлено»
   в логе выглядит как успех, и перепутать легко.

Сменить шлюз — это соседний класс рядом с `providers/smsru.py` и строка в
`.env`. У SMSC, SMS Aero и P1SMS API устроены так же: POST с ключом и
разбор JSON. Прикладной код не меняется, он работает через `SmsProvider`.

### Временные и постоянные ошибки

Шлюз отвечает двумя уровнями статусов: общим на запрос и отдельным на
каждый номер. Неверный ключ виден в первом, недоступный номер — только во
втором, поэтому разбираются оба.

| Класс ошибки | Исключение | Что делает система |
|---|---|---|
| шлюз не ответил, таймаут, HTTP 5xx, не-JSON | `SmsDeliveryError` | 5 повторов Celery с нарастающей паузой |
| неверный ключ, нет денег, не зарегистрирован отправитель, номер в стоп-листе | `SmsRejectedError` | помечает уведомление неудачным и останавливается |

Разделение нужно, чтобы не крутить пять повторов подряд там, где чинить
надо настройки, а не ждать. Список постоянных кодов — в `PERMANENT_CODES`
в `providers/smsru.py`.

Остаток на счету приходит в каждом ответе шлюза и пишется в лог: это
бесплатный способ узнать, что деньги кончаются, до того как отправка
встанет.

### Как платить меньше

Основной расход — не коды входа, а сопровождение записи. На одну бронь
сейчас приходится три SMS (создана, напоминание, выполнена) плюс код входа.

`SMS_ENABLED_KINDS` перечисляет типы, которые реально уходят. Всё, что не
попало в список, остаётся в журнале со статусом «Не отправляли»: тихо
выбрасывать запись нельзя, «клиенту не сообщили» — такой же факт, как
«сообщили», и он должен быть виден.

Разумный минимум:

```bash
SMS_ENABLED_KINDS=otp,booking_reminder,booking_cancelled_by_master
```

- **код входа** — без него нельзя войти;
- **напоминание за 2 часа** — окупается снижением неявок;
- **отмена сервисом** — клиент обязан узнать, что его визит отменили.

Отключаются «запись создана» и «работы выполнены»: и то, и другое клиент
видит в приложении в момент действия. Это убирает две SMS из трёх на
каждую бронь.

Что ещё снижает расходы:

- **Звонок-подтверждение вместо SMS** для кодов входа: клиенту звонят, код —
  последние цифры номера звонящего. У тех же операторов он стоит заметно
  дешевле SMS. Потребует отдельного провайдера рядом с `smsru.py`.
- **Push вместо SMS** для сопровождения записи. В модели `Notification`
  канал `push` уже предусмотрен, отправка не реализована.
- **Лимиты OTP** уже стоят и экономят на переборе: пауза 60 секунд между
  отправками и 5 кодов на номер в час.

## Фоновые задачи

| Задача | Период | Зачем |
|---|---|---|
| `expire_stale_drafts` | 20 секунд | освободить слот брошенного черновика |
| `send_booking_reminders` | 5 минут | SMS за 2 часа до визита, ровно один раз |
| `purge_old_drafts` | сутки | удалить мёртвые черновики старше 7 дней |
| `purge_expired_otp` | час | почистить использованные коды |

Расписание — `CELERY_BEAT_SCHEDULE` в `config/settings/base.py`.

Напоминание защищено от дублей: задача сначала «занимает» запись
условным `UPDATE … WHERE reminder_sent_at IS NULL`, и только потом шлёт SMS.
Повторный запуск задачи не отправит второе сообщение.

Свежие закрытые черновики намеренно не удаляются сразу — по ним видно, на каком
шаге люди отваливаются.

## Конфигурация

Все настройки читаются из `.env` через `django-environ`. Шаблон — `.env.example`.

### Бизнес-правила

Собраны в `settings.BOOKING` и `settings.OTP` — единая точка правды. Меняются без
правок кода:

```bash
BOOKING_DRAFT_TTL_SECONDS=300        # жизнь черновика (требование: 5 минут)
BOOKING_MIN_LEAD_MINUTES=30          # нельзя записаться «через минуту»
BOOKING_HORIZON_DAYS=14              # на сколько дней вперёд открыта запись
BOOKING_CANCEL_DEADLINE_MINUTES=60   # до какого момента клиент отменяет сам
BOOKING_REMINDER_LEAD_MINUTES=120    # за сколько минут напоминать
BOOKING_DRAFT_PURGE_AFTER_DAYS=7     # когда физически удалять мёртвые черновики

OTP_TTL_SECONDS=300
OTP_RESEND_COOLDOWN_SECONDS=60
OTP_MAX_VERIFY_ATTEMPTS=5
OTP_MAX_PER_PHONE_PER_HOUR=5
OTP_DEBUG_EXPOSE_CODE=True           # ⚠ в проде обязательно False
```

### Контакты компании

Всё, что показывает лендинг, кроме цен и адресов, задаётся в `.env`:

```bash
COMPANY_NAME=Мой Сервис
COMPANY_TAGLINE=Замена масла по записи
COMPANY_PHONE=+7 (499) 123-45-67
COMPANY_EMAIL=hello@example.com
COMPANY_WORKING_HOURS=Ежедневно 09:00–21:00
COMPANY_APP_STORE_URL=           # пусто = кнопка «скоро», без перехода
COMPANY_GOOGLE_PLAY_URL=
COMPANY_SHOW_PRICES=false       # false = на сайте только ассортимент, без сумм
COMPANY_YEARS_ON_MARKET=8
COMPANY_CARS_SERVED=14000
```

Длительности замены на витрине намеренно нет. Обещание «за N минут» —
это то, что клиент проверит секундомером в первый же визит, а замена
зависит от машины: слить отработку с прогретого мотора и с холодного —
разное время. Витрина обещает своё время приезда и отсутствие очереди,
а не скорость работы.

Цены и адреса на лендинг попадают из базы (`Oil`, `ServicePoint`) — там же, откуда
их берёт API.

### Часовые пояса

В базе **всё в UTC** (`TIME_ZONE = "UTC"`, `USE_TZ = True`). Локальное время берётся
из `ServicePoint.timezone` для каждой точки отдельно. `BUSINESS_TIMEZONE` — пояс,
в котором сотрудники думают о «сегодня», используется в сводке за день.

Вторая точка в другом регионе ничего не сломает.

| `tests/test_master_stream.py` | канал сотрудника: клиента не пускает, подписка по своим точкам, сигналы о записи и отмене, чужая точка молчит, персональные данные в канал не уходят |

Тесты идут с `django_db(transaction=True)` — иначе не сработали бы колбэки
`transaction.on_commit`, а значит не проверялись бы уведомления.

Время подкручивается `freezegun`. Фикстура `free_slot` намеренно берёт слот
**на завтра**: тесты двигают часы на минуты вперёд, и слот не должен из-за этого
упираться в минимальный запас до визита.

## Веб-интерфейс

Чистые HTML, CSS и JavaScript — без сборщика, фреймворков и внешних зависимостей.

| Адрес | Кому | Что там |
|---|---|---|
| `/` | клиенту | лендинг: о компании, ассортимент масел, адреса, ссылки на приложения, телефон для записи |
| `/master/` | мастеру | смена в реальном времени: сводка, фильтры, действия, живые черновики |
| `/admin-panel/` | администратору | всё то же плюс вкладка метрик |

`/admin-panel/`, а не `/admin/`: последний занят Django-админкой, и она остаётся
инструментом для правки справочников.

### Лендинг

Витрина, а не приложение: **работает без JavaScript**. Масла и адреса рендерятся
на сервере из тех же таблиц, что отдаёт API, — витрина не разъедется с тем, что
клиент увидит в приложении.

Страница одета по фирменному знаку «Мой Сервис»: почти чёрный фон с синим
подтоном, контуры неоновой трубкой, «хромированные» надписи. Поэтому **лендинг
всегда тёмный и переключателя темы на нём нет**: неон на белом фоне не светится,
а светлый вариант витрины читался бы как другая компания. Светлая и тёмная темы
остались там, где ими действительно пользуются, — в панелях сотрудников.

Структура осталась прежней (утилитарная полоса, первый экран во всю ширину,
полоса цифр, разноразмерные плитки, масла, два пути записи, адреса карточками,
блок приложения, FAQ на `<details>`, полоса с телефоном), изменились подача и
материал: вместо плоских светлых карточек — «стекло» с волосяной градиентной
рамкой, вместо оранжевого акцента — синий неон логотипа.

#### Цены на сайте — по флагу

`COMPANY_SHOW_PRICES` решает, что показывать в секции «Расходные материалы»:

| Значение | Что на сайте | Заголовок и меню |
|---|---|---|
| `false` (по умолчанию) | карточки: бренд, название, вязкость, тип, объём | «Расходные материалы», пункт меню «Расходные материалы» |
| `true` | таблица с ценой материала, ценой работы и итогом | «Расходные материалы и цены», пункт меню «Цены» |

Заказчик может не хотеть раскрывать стоимость публично. Совсем убирать секцию
при этом неправильно: клиенту важно увидеть, что нужное ему есть, — а сумму он
узнаёт по телефону или в приложении. Данные в обоих случаях одни и те же, из
таблицы `Oil`.

Остатков на складе на витрине нет ни в одном из режимов: сколько канистр
лежит на точке — внутренняя информация, и показывать её клиенту незачем.
Слово «канистра» в обращении к клиенту тоже не используется — только
«расходные материалы».

Карточками, а не таблицей: таблица с колонками «вязкость, тип, объём» и без
суммы читается как прайс, у которого забыли последний столбец.

#### Фирменный знак

`templates/web/_logo.html` — силуэт машины неоновой трубкой и надпись поверх
него. Нарисован вектором, а не картинкой: знак стоит в шапке, на первом экране
и в подвале, растровый файл пришлось бы возить в трёх размерах.

- Свечение даётся CSS-фильтром `drop-shadow` в три слоя, а не SVG-фильтром: тот
  пришлось бы объявлять в `defs`, а знак на странице встречается трижды —
  получились бы дубли `id`.
- Размер задаётся одной переменной `--logo-w`, от неё считается и надпись, —
  пропорции лока не зависят от того, где он стоит.
- Крыша и порог выходят из одной точки слева: этот клин и читается как нос
  машины, без схождения остаются просто две дуги.
- Длину каждой линии измеряет `landing.js` и кладёт в переменную `--len`:
  прошитая в CSS константа обрезала бы чужой рисунок или оставляла его мигать.
- Слова в знаке заданы текстом в шаблоне, а не берутся из `COMPANY_NAME`: это
  рисунок, а не подпись. Название компании в `.env` должно ему соответствовать —
  в подвале и в `<title>` выводится именно оно.

#### Как подставить свой рисунок знака

Меняется один блок в `templates/web/_logo.html` — `<g class="logo-lines">`.
Ни CSS, ни JS трогать не нужно: длину каждой линии `landing.js` измеряет сам
(`getTotalLength`) и кладёт в переменную `--len`, а блик делает копией пути.
Поэтому анимация повторится на любой геометрии, ничего подгонять руками не
придётся.

**Рисунок бывает двух видов, и от этого зависит анимация.**

*Заливка* — линия задана границами самой ленты, замкнутым контуром. Так
нарисован текущий знак: группа помечена `logo-lines-solid`, атрибут
`fill="none"` убран. Толщина получается переменной, с сужением к носу и
корме, — у ровной обводки такого не бывает, и для неона это выглядит
лучше. Плата: прочерчивания нет, знак загорается разом. Мигание «розжига»,
свечение и бегущий блик работают.

*Осевые линии* — каждая линия отдельный `<path>` с обводкой. Тогда знак
прочерчивается от начала к концу, линия за линией. Для этого группе нужен
`fill="none"` и никакого `logo-lines-solid`.

**Требования к осевому варианту.** Без них прочерчивание не заработает:

1. **Линии должны быть обводкой (`stroke`), а не заливкой (`fill`).** Знак
   загорается тем, что обводка прочерчивается от начала к концу; у залитой
   фигуры чертить нечего. В Illustrator это значит не применять
   Object → Expand, в Figma — оставить Stroke и не делать Outline stroke.
2. **Каждая линия — отдельный `<path>`.** `<line>`, `<polyline>`, `<circle>`,
   `<rect>` тоже подойдут. А вот `<g>` с вложенными фигурами анимируется
   целиком, как один объект.
3. **Каждому пути нужен `class="logo-line"`.**
4. **Ни `fill`, ни `stroke`, ни `filter` в самом SVG прописывать не надо** —
   цвет и свечение приходят из CSS. Экспорт с инлайновыми стилями
   («Presentation attributes» в Illustrator) их перебьёт: такие атрибуты
   нужно удалить.
5. **Порядок путей в разметке = порядок, в котором они загораются.**
   Задержки стоят в `landing.css` на `.logo-line:nth-child(1..6)`.
6. **`viewBox` подставьте свой** — пропорции знака берутся из него. Атрибуты
   `width` и `height` у `<svg>` не нужны, размер задаёт CSS.
7. **Одному пути добавьте `data-spark`** — самому длинному и заметному,
   обычно линии крыши. По нему раз в семь секунд пробегает блик-отражение.

**Порядок действий:**

1. Нарисовать знак линиями в Illustrator, Figma, Inkscape — где удобно.
2. Экспортировать в SVG. В Figma: Export → SVG, галочки «Include id
   attribute» и «Outline text» снять. В Illustrator: File → Export →
   SVG, Styling → «Internal CSS», Object IDs → «Minimal».
3. Открыть файл текстовым редактором, забрать оттуда `viewBox` и сами
   `<path d="…">`.
4. В `_logo.html` заменить содержимое `<g class="logo-lines">` своими
   путями, каждому дописать `class="logo-line"`, одному — `data-spark`.
5. Толщину линий править в `landing.css`: либо общую у `.logo-line`, либо
   отдельным классом конкретному пути.

**Проверить, что получилось**, удобнее всего в консоли браузера на главной:

```js
[...document.querySelectorAll('.logo-line')]
  .map(l => [l.getAttribute('class'), l.style.getPropertyValue('--len')])
```

У каждой линии должно стоять число — измеренная длина. Пусто означает, что
фигура не поддерживает `getTotalLength` (скорее всего это `<g>`), и такую
линию нужно разбить на отдельные пути.

Для варианта с заливкой из этих требований обязателен только пункт 6
(`viewBox`) и пункт 7 (`data-spark`): всё остальное относится к обводке.

**Надпись** («Мой Сервис», одной строкой поперёк кузова) набрана текстом
поверх рисунка и красится хромовым градиентом в CSS, а не нарисована в SVG:
так она берётся из одной строки шаблона и не требует перерисовки кривых при
смене названия. Если буквы уже нарисованы внутри SVG, удалите из
`_logo.html` блок `<span class="logo-word">`, иначе надпись задвоится.

Два решения в надписи:

- **Размеры считаются от `--logo-w`, а не в процентах от высоты бокса.**
  Высота знака зависит от пропорций рисунка, и при его замене проценты
  поехали бы вместе с ней.
- **Строка растянута по горизонтали** (`scaleX(1.1)`): на образце гарнитура
  заметно шире Arial Black. Тянуть ради одного слова веб-шрифт — лишний
  запрос, вес и мигание при загрузке, а лёгкое искажение на таком кегле
  незаметно.

**При смене названия подбирайте кегль и посадку заново.** Оба заданы долей
от `--logo-w` (сейчас `.078` и `.137`). Слово другой длины либо вылезет за
габарит кузова, либо потеряется на нём, а строка не должна наезжать на
линии машины: надпись стоит *под* линией борта, а не поперёк неё. Проверить
пересечения можно в консоли браузера — `isPointInFill()` по сетке точек
внутри текстового бокса:

```js
const L = document.querySelector('.logo-hero');
const svg = L.querySelector('.logo-car');
const path = L.querySelector('.logo-line-body');
const r = document.createRange();
r.selectNodeContents(L.querySelector('.logo-word-main'));
const t = r.getBoundingClientRect();
const m = svg.getScreenCTM().inverse();
let hits = 0;
for (let i = 0; i <= 80; i++) for (let j = 0; j <= 24; j++) {
  const p = svg.createSVGPoint();
  p.x = t.left + t.width * i / 80;
  p.y = t.top + t.height * j / 24;
  if (path.isPointInFill(p.matrixTransform(m))) hits++;
}
hits;   // попадания в верхней полосе — это межстрочный отступ, не буквы
```

Заодно проверьте, что знак по-прежнему влезает в шапку: её высоту задаёт
`--header-h` на `.landing`.

#### Движение

Анимация на странице делает ровно три вещи и ничего сверх:

1. **Бренд.** При открытии трубка «схватывается» с неровным миганием —
   проценты в `@keyframes neon-ignite` намеренно неравномерные, ровный fade
   выдал бы обычное появление картинки. Дальше раз в семь секунд по кузову
   пробегает короткий блик; большую часть цикла он стоит за краем кадра,
   витрина не должна мигать. Прочерчивание линий у текущего знака не
   работает — он нарисован заливкой, подробности выше.
2. **Появление блоков.** Один раз, на 14 px, без возврата при обратной
   прокрутке: повторный выезд читается как баг, а не как оформление. Соседи в
   группе идут с задержкой по индексу, но не больше шести шагов — дальше выход
   блока превращается в ожидание. Кривая одна на весь лендинг
   (`--ease: cubic-bezier(.22, 1, .36, 1)`): разнобой в ускорениях и делает
   анимацию самодельной.
3. **Реакция на курсор.** Блик под указателем на стеклянных карточках (это
   отражение, поэтому он следует за мышью, а не просто «подсвечивает»),
   зажигание строки прайса и подчёркивание в меню, разъезжающееся из центра.

Мокап приложения на первом экране — не картинка, а короткий показ сценария
записи: шаги загораются по очереди, выбирается время, утекает таймер брони, в
конце нажимается подтверждение. Цикл 12 секунд, целиком на CSS — так одна строка
`prefers-reduced-motion` выключает его вместе со всем остальным, а JS только
ставит его на паузу, когда мокап уехал с экрана.

Правила, которые держат этот слой:

- **Страница обязана работать без `landing.js`.** Он ничего не рендерит, только
  доигрывает отрисованное сервером. Блоки прячутся классом `has-js`, который
  ставится инлайновым скриптом в `<head>` до отрисовки: нет JS — нет класса, всё
  видно. Если что-то в скрипте упало, `catch` показывает все блоки разом.
- **Обработчиков прокрутки и движения мыши ровно по одному**, и оба сведены в
  `requestAnimationFrame`. Границы карточки читаются только при смене цели:
  `getBoundingClientRect` на каждое движение мыши заставляет браузер
  пересчитывать раскладку.
- **Счётчики на первом экране докручиваются один раз** по `easeOutExpo` и только
  когда доехали до экрана. Не сработал `IntersectionObserver` — в разметке уже
  лежит готовое число с сервера.
- **`prefers-reduced-motion` выключает всё**, но неон при этом горит, а не
  остаётся недорисованным.

Записи на сайте нет намеренно: клиент записывается в приложении или по телефону,
и веб-форма дублировала бы сценарий, за которым нужно следить в двух местах.

Контакты и ссылки на магазины лежат в `.env` (`settings.COMPANY`): телефон и
ссылки меняет не программист, и правка не должна требовать ни редактирования
кода, ни пересборки образа. Пока ссылка пустая, кнопка магазина показывается
неактивной с пометкой «скоро» — а не ведёт в никуда.

### Панели сотрудников

```
static/web/css/app.css     дизайн-система: переменные, светлая и тёмная темы
static/web/css/landing.css стили лендинга — грузятся только на главной
static/web/js/core.js      запросы к API, обновление токена, тосты, тема, формат
static/web/js/landing.js   движение на лендинге — грузится только на главной
static/web/js/staff.js     смена: реальное время, фильтры, действия по записям
static/web/js/metrics.js   метрики администратора и графики в SVG
```

- **Список живёт в реальном времени.** Канал `ws/master/` присылает сигнал, панель
  перечитывает текущую выборку. Опрос раз в 20 секунд остаётся, но включается
  только когда канал недоступен: реальное время не должно зависеть от того,
  разрешён ли WebSocket в сети клиента. Состояние связи видно в шапке смены.
- **Время показывается в часовом поясе точки**, а не браузера: `local_time`
  приходит с сервера. Мастер в другом регионе увидит то же, что и клиент.
- **Токены клиента и сотрудника лежат под разными ключами `localStorage`.**
  За одним браузером сидит один человек, но роли у него разные.
- **`access` обновляется молча.** Он живёт час; при `401` `core.js` меняет его по
  `refresh` и повторяет запрос — вкладка, открытая с утра, не начинает сыпать
  ошибками.
- **Заход не на свою панель не рвёт сессию.** Мастер на `/admin-panel/` видит
  объяснение и ссылку на своё рабочее место, а не разлогин.
- **Графики нарисованы вручную в SVG.** Данных немного, зато диаграммы сами
  подхватывают цвета темы из CSS-переменных и не тянут стороннюю библиотеку.
- **Тема переключается кнопкой и запоминается**, а по умолчанию берётся из
  системной настройки (`prefers-color-scheme`).

### Раздача статики

В разработке HTTP-приложение обёрнуто в `ASGIStaticFilesHandler` (`config/asgi.py`).
Daphne — не `runserver`: сам он статику не отдаёт, а `staticfiles` подменяет
обработчик только в команде `runserver`, поэтому без обёртки CSS и JS отдавались
бы как `404`. При `DEBUG=False` обёртки нет — в проде статику раздаёт nginx
перед daphne.

## Мобильное приложение

Клиентское приложение под Android лежит в [`mobile/android`](mobile/android) —
Java, Android Studio, без Kotlin. Открывать в студии нужно именно эту папку.

| Что | Значение |
|---|---|
| Минимальная версия | Android 7.0 (API 24) |
| Собирается под | API 35 |
| Архитектура | MVVM: `ui` → `domain` → `data`, зависимости внутрь |
| Сеть | Retrofit + OkHttp, WebSocket для живого статуса записи |
| Токены | `EncryptedSharedPreferences`, ключ в Android Keystore |

Экраны: вход по SMS, запись в четыре шага с таймером, свои записи с отменой,
профиль. Палитра и типографика повторяют лендинг.

Отладочная сборка ходит на `http://10.0.2.2:8000` — так эмулятор видит
`localhost` хост-машины. Открытый HTTP разрешён **только** для этого адреса и
только в debug; в релизе обязателен `https`.

Подробности — сборка, подпись, чек-лист Play Console и список того, что
осознанно не вошло в первую версию, — в
[`mobile/android/README.md`](mobile/android/README.md).

## Известные ограничения и подводные камни

1. **Кириллица в пути ломает `docker compose build`** без имени сервиса. Обход —
   `docker compose build api` (в `Makefile` уже так). Подробности — в разделе
   «Быстрый старт».
2. **`OTP_DEBUG_EXPOSE_CODE=True` возвращает код входа прямо в ответе API.** Удобно
   в разработке, недопустимо в проде.
3. **График «через полночь» не поддерживается** осознанно: если `closes_at <= opens_at`,
   слоты на день не строятся. Для круглосуточной точки ставьте `00:00`–`23:30`.
4. **Push-уведомлений нет** — только SMS. Модель `Notification` уже имеет поле
   `channel` со значением `push`, но отправка не реализована.
5. **Записи на сайте нет** — это осознанное решение: клиент записывается в
   приложении или по телефону. Сценарий записи полностью живёт в API.
6. **Онлайн-оплаты нет.** Цены фиксируются в записи, расчёт на месте.
7. **Реферальная программа не видна снаружи.** Ядро готово, но клиент не видит
   свой код приглашения, а мастер не может списать баллы при расчёте — экранов
   для этого ещё нет. Подробности в разделе «Реферальная программа».
8. **Один сервис — замена масла.** Модели `Oil`/`OilStock` заточены под канистры;
   для второй услуги понадобится ввести сущность «услуга».
9. **Мастер не привязан к записи автоматически** — поле `master` заполняется, когда
   он берёт запись в работу.
10. **Отмена клиентом возможна только из статуса `pending`.** Если мастер уже начал
   работу, отменить нельзя.

## Деплой на сервер

Базовый `docker-compose.yml` рассчитан на разработку: он пробрасывает наружу
порты PostgreSQL, Redis и daphne. На машине с публичным адресом так нельзя —
Redis без пароля находят автоматические сканеры за минуты. Поэтому на проде
compose запускается с надстройкой `docker-compose.prod.yml`, которая эти порты
убирает, собирает образ без dev-зависимостей и монтирует статику в каталог
хоста для nginx.

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
```

### Порядок развёртывания

1. **Docker и nginx на сервере.** Docker — из официального репозитория, а не
   `docker.io` из Ubuntu: надстройке нужен Compose не ниже 2.24 (теги `!reset`),
   а в системных репозиториях он бывает старее.
   ```bash
   curl -fsSL https://get.docker.com | sh
   apt update && apt install -y git nginx certbot python3-certbot-nginx
   docker compose version   # должно быть 2.24 или выше
   ```
2. **Клонировать в `/opt/auto_service`** (этот путь прописан в примере конфига
   nginx) и создать каталоги статики:
   ```bash
   git clone https://github.com/Nikita885/auto_service.git /opt/auto_service
   cd /opt/auto_service && mkdir -p static media && chown -R 1000:1000 static media
   ```
   `1000` — uid пользователя `appuser` внутри контейнера. Без этого
   `collectstatic` упрётся в права хоста.
3. **Заполнить `.env`** по чек-листу ниже. Ключ генерируется так:
   ```bash
   python3 -c "import secrets; print(secrets.token_urlsafe(50))"
   ```
4. **Поднять контейнеры** командой выше.
5. **Настроить nginx**: скопировать [`deploy/nginx.conf.example`](deploy/nginx.conf.example)
   в `/etc/nginx/sites-available/autoservice`, слинковать в `sites-enabled`,
   проверить `nginx -t` и перезагрузить.
6. **Выпустить сертификат** — бесплатный Let's Encrypt, продлевается сам.
   Перечислять нужно все имена, включая те, что только редиректят: сертификат
   предъявляется до редиректа, и без имени в нём браузер покажет ошибку
   безопасности вместо перехода.
   ```bash
   certbot --nginx -d <домен> -d www.<домен> -d <домен-2> -d www.<домен-2>
   ```
7. **Создать администратора**, раз демо-данных на проде нет:
   ```bash
   docker compose -f docker-compose.yml -f docker-compose.prod.yml exec api \
       python manage.py createsuperuser
   ```

### Обновление уже развёрнутого сервера

```bash
cd /opt/auto_service
git pull
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
```

Почему именно перезапуск контейнера, а не просто `git pull`:

- **Шаблоны кешируются в памяти процесса.** При `DEBUG=False` Django сам
  оборачивает загрузчики в `cached.Loader`. Прод-надстройка монтирует код с
  хоста (`.:/app`), то есть новый HTML лежит на месте сразу — но daphne
  продолжает отдавать разобранный старый, пока его не перезапустят.
- **`collectstatic` запускается в `entrypoint.sh` при старте `api`.** Пока
  контейнер не перезапущен, в `static/` лежит прошлая сборка CSS и JS.
- `--build` нужен, только если менялись зависимости; в остальных случаях
  достаточно `restart api`, но лишним он не будет.

Миграции применяются тем же entrypoint автоматически. Изменения, которые
трогают только вёрстку и стили, миграций не требуют вовсе.

**После правки `.env` контейнер тоже надо перезапустить** — переменные
окружения читаются один раз при старте. `.env` в репозиторий не входит, так что
новые ключи после `git pull` не появятся сами: сверяйтесь с `.env.example`.

### Почему имена файлов статики с хешем

В проде `STORAGES` подменяет хранилище на хеширующее: `{% static %}` отдаёт
`landing.a1b2c3d4.css` вместо `landing.css`, и nginx раздаёт `/static/` с
`Cache-Control: immutable` на год.

Причина простая. HTML браузер не кеширует — его каждый раз рендерит Django. CSS
по неизменному адресу он кеширует надолго. Значит после выкатки нового
оформления вернувшийся посетитель получил бы **новую разметку со старыми
стилями** — то есть сломанную страницу, и чинилась бы она сама только когда
истечёт срок жизни кеша. Задним числом чужой браузерный кеш не сбрасывается
ничем, кроме смены адреса файла.

Хранилище намеренно «прощающее» (`manifest_strict = False`,
`apps/common/staticfiles.py`): `collectstatic` в entrypoint запускается с
`|| true`, и если он однажды упадёт, файл без записи в манифесте отдастся по
имени без хеша, а не уронит страницу пятисоткой.

### Кириллический домен

Если доменов два — латинский и кириллический, — основным стоит делать
латинский, а кириллический редиректить на него (так сделано в примере конфига
nginx). Иначе punycode придётся тащить в `ALLOWED_HOSTS`, в сборку Android-
приложения и в каждую внешнюю интеграцию, и каждое из этих мест — отдельный
шанс ошибиться в строке, которую невозможно прочитать глазами.

Домен вида `экспрес-замена.рф` в заголовке `Host` приходит в **punycode**
(`xn----8sbarcksuknlkd6n.xn--p1ai`), и certbot работает только с этой формой.
В `ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS`, `CORS_ALLOWED_ORIGINS` и
`server_name` нужен именно punycode — с кириллицей в `ALLOWED_HOSTS` Django
ответит `400 Bad Request` на каждый запрос. Перевести домен можно так:

```bash
python3 -c "print('экспрес-замена.рф'.encode('idna').decode())"
```

### Почему в nginx нужен `X-Forwarded-Proto`

В прод-настройках включён `SECURE_SSL_REDIRECT`, а схему запроса Django берёт
из `SECURE_PROXY_SSL_HEADER`. Если nginx не передаст этот заголовок, Django
сочтёт запрос пришедшим по HTTP и отправит редирект на HTTPS — который nginx
снова проксирует на тот же обработчик. Получится бесконечная петля редиректов.
В примере конфига заголовок проставлен во всех секциях.
