# Автосервис — бэкенд записи на замену масла

Backend-платформа для сети автосервисов, оказывающих одну услугу — замену масла.
API обслуживает мобильные приложения — клиентское и приложение мастера.

Сайт записью не занимается: клиент записывается в приложении или по телефону.
В вебе живут лендинг с информацией о компании и ссылками на магазины приложений,
рабочее место мастера и панель администратора с метриками.

**Стек:** Django 5.1 · Django REST Framework · PostgreSQL 16 · Celery + Redis ·
JWT (simplejwt) · Django Channels (WebSocket) · Docker Compose

**Статус:** серверная часть готова и проверена — 440 тестов, линтер чистый,
сквозной сценарий прогнан по живому HTTP. В вебе работают лендинг и панели
сотрудников; записи у мастера обновляются в реальном времени. Клиент — одно
веб-приложение `/app/`: на iPhone с главного экрана, на Android — в
приложении-оболочке (`mobile/android`). Приложения мастера нет.

## Что умеет система

### Клиент

Записывается в мобильном приложении или звонком по телефону — на сайте формы
записи нет. Всё перечисленное ниже доступно через API, на котором работают
приложения.

1. Входит по номеру телефона — **пароля нет вообще**, только код из SMS.
2. Заполняет профиль: имя и свои автомобили — их может быть несколько, один основной.
3. Записывается на замену масла в четыре шага: **адрес → масло → время → подтверждение**;
   на подтверждении выбирает, какую из своих машин привезёт.
4. С момента нажатия «Записаться» у него **5 минут** на прохождение всех шагов.
   Не успел — черновик сгорает, начинать заново.
5. Видит статус процесса в реальном времени: на каком шаге, что уже выбрано,
   сколько секунд осталось.
6. Может отменить свою бронь (не позже чем за час до визита).
7. Получает SMS: подтверждение записи, напоминание за 2 часа, уведомление об отмене.

### Мастер (вторая версия приложения)

1. Видит список записей **в реальном времени**: новая запись, отмена и смена
   статуса появляются на экране сами, без перезагрузки.
2. В списке — время, код, **имя клиента, телефон, автомобиль, выбранное масло**.
3. Фильтрует по дате, статусу, точке; ищет по коду / имени / телефону / госномеру.
4. Ведёт запись по статусам: взять в работу → выполнено / клиент не приехал.
5. Отменяет запись с обязательной причиной — клиенту **автоматически** уходит SMS.
6. Видит, кто записывается прямо сейчас (незавершённые черновики).
7. Смотрит сводку за день: сколько записей, выполнено, отменено, выручка.
8. **Записывает клиента сам** — тот позвонил или приехал без записи
   (см. «Запись клиента мастером»).

### Администратор

1. Всё, что доступно мастеру: смена, фильтры, действия по записям, живые черновики.
2. **Метрики по сети** за произвольный период: выручка с разбивкой на масло и работу,
   средний чек, доли выполненных, отменённых и неявок.
3. **Воронка записи** — на каком шаге клиенты отваливаются и сколько черновиков
   сгорело по таймеру.
4. Динамика по дням, загрузка по часам, сравнение точек, ходовые позиции масла,
   остатки склада с подсветкой заканчивающихся, приток клиентов.
5. Django-админка: точки, масла, остатки на складе, пользователи, записи, журнал SMS.

## Быстрый старт

```bash
git clone https://github.com/Nikita885/auto_service.git
cd auto_service
cp .env.example .env
docker compose build api && docker compose up -d
```

или просто `make up`.

> **Почему `build api`, а не просто `build`.** На машине разработчика проект лежит
> по пути с кириллицей (`…/Никита/Автосервис`), а `docker compose build` без имени
> сервиса падает: BuildKit не умеет не-ASCII в ключе сессии
> (`header key "x-docker-expose-session-sharedkey" contains value with
> non-printable ASCII characters`). Сервисы `worker` и `beat` используют тот же
> образ, что и `api`, поэтому одной сборки достаточно. Если склонировать репозиторий
> в путь без кириллицы — работает и обычный `docker compose up --build`.

Первый старт автоматически применит миграции и зальёт демо-данные: 2 адреса,
4 позиции масла, остатки на складе, учётки сотрудников.

| Что | Адрес |
|---|---|
| Лендинг | http://localhost:8000/ |
| Рабочее место мастера | http://localhost:8000/master/ |
| Панель администратора с метриками | http://localhost:8000/admin-panel/ |
| Swagger UI | http://localhost:8000/api/docs/ |
| ReDoc | http://localhost:8000/api/redoc/ |
| OpenAPI JSON | http://localhost:8000/api/schema/ |
| Django-админка | http://localhost:8000/admin/ |
| Healthcheck | http://localhost:8000/health/ |

**Демо-учётки** (создаются командой `bootstrap_demo`):

| Роль | Телефон | Пароль (только для админки) |
|---|---|---|
| Администратор | `+79000000000` | `admin12345` |
| Мастер | `+79000000001` | `master12345` |

В API оба заходят по SMS-коду, как обычные пользователи. Пароль нужен только для
входа в Django-админку.

**Как получить SMS-код в разработке.** При `OTP_DEBUG_EXPOSE_CODE=True` код
возвращается прямо в ответе `POST /api/v1/auth/otp/request/` в поле `debug_code`,
и дополнительно печатается в логи воркера (`docker compose logs worker`).
SMS-шлюз для разработки не нужен.

### Сервисы в Docker Compose

| Сервис | Что это |
|---|---|
| `api` | Daphne (ASGI) — HTTP + WebSocket, порт 8000 |
| `worker` | Celery worker — отправка SMS |
| `beat` | Celery beat — периодические задачи |
| `db` | PostgreSQL 16, порт 5432 |
| `redis` | Redis 7 — брокер Celery, кеш, channel layer |

У всех пяти сервисов стоит `restart: unless-stopped` и ограничение на
размер логов (`json-file`, 10 МБ × 5 файлов). Первое — чтобы сайт
поднимался после перезагрузки сервера сам: без политики перезапуска у `db`
и `redis` контейнер `api` уходил бы в бесконечный рестарт. Второе — потому
что json-file по умолчанию пишет, пока не кончится диск, а «no space left
on device» первым получает PostgreSQL.

`api`, `worker` и `beat` — это **один образ** с разной командой запуска
(YAML-якорь `x-app` в `docker-compose.yml`). Так гарантируется, что версия кода
в веб-процессе и в фоновых задачах не разъезжается.

### Правило слоёв

Это главное архитектурное решение проекта.

```
HTTP-запрос → View → Serializer (валидация формата) → Service (бизнес-логика) → ORM
```

**Вьюха** разбирает вход сериализатором, вызывает функцию из `services/` и отдаёт
результат. Бизнес-`if`-ов во вьюхах нет ни одного.

**Сервис** ничего не знает про HTTP. Он бросает доменные исключения
(`ConflictError`, `GoneError`, `NotFoundError`, …). Благодаря этому один и тот же
сценарий вызывается из HTTP-вьюхи, из Celery-задачи, из management-команды и из
тестов — без дублирования логики.

**Превращение исключения в HTTP-ответ** происходит ровно в одном месте —
`apps/common/exceptions.py::api_exception_handler`.

### Единый формат ошибки

Любая ошибка API выглядит одинаково:

```json
{
  "error": {
    "code": "slot_taken",
    "message": "Это время уже заняли",
    "details": {}
  }
}
```

Мобильный клиент разбирает машиночитаемый `code`, а не текст сообщения — тексты
можно править и переводить, не ломая приложения.

## Модель данных

### `accounts.User`

Логин — телефон в формате E.164. Один пользователь на любую роль.

| Поле | Описание |
|---|---|
| `id` | UUID — публичные id не раскрывают количество клиентов |
| `phone` | уникальный, E.164 (`+79001234567`) |
| `full_name` | имя |
| `role` | `client` / `master` / `admin` |
| `service_points` | M2M: точки мастера. Пусто = доступ ко всем |
| `is_active`, `is_staff`, `date_joined` | стандартные |

У клиента пароль **unusable** — войти можно только по SMS. У мастера и админа
пароль есть, но только чтобы зайти в Django-админку.

Машины клиента — в `garage.Car` (ниже). Поля `car_model`/`car_plate` в
профиле были до появления гаража; миграция `garage.0002` перенесла их в
первую машину, `accounts.0004` удалила. В ответе `/auth/me/` они остались
строками основной машины — для сборок приложений, которые знают одну
машину в профиле, — и `PATCH` по ним правит основную машину.

### `garage.Car`

Автомобиль клиента. Их у клиента сколько угодно (защитный потолок —
`GARAGE_MAX_CARS`, 10), основной — ровно один.

| Поле | Описание |
|---|---|
| `user` | владелец |
| `title` | «марка и модель» свободной строкой — справочник подсказывает, но не ограничивает |
| `make`, `model` | ссылки на справочник, если клиент выбрал подсказку |
| `plate` | госномер в одной форме: кириллица, без пробелов (`a 123 bc` → `А123ВС`) |
| `year`, `mileage`, `vin` | необязательные; VIN — 17 знаков без I, O, Q |
| `is_primary` | основной: его подставляет запись; первый добавленный — основной сам |
| `archived_at` | удалён клиентом — мягко: на машину ссылаются записи |

- **Основной ровно один** — частичный уникальный индекс
  `uniq_primary_car_per_user`, а все изменения машин одного клиента идут
  под блокировкой строки его аккаунта: два параллельных «добавить первую
  машину» не сделают основными обе.
- **Номер приводится к одной форме**, потому что его набирают и клиент
  (латиницей), и мастер (кириллицей), а искать по нему должно одинаково.
  Номер с буквами вне русского набора (иностранный) не трогается, кроме
  регистра и пробелов.
- **Удаление мягкое**: удалённая машина пропадает из гаража, но записи на
  неё и их снимки остаются как были. Удалили основную — основной
  становится последняя добавленная из оставшихся.
- **Перенос из профиля** (`garage.0002`, `booking.0004`): непустые
  `car_model`/`car_plate` стали первой машиной клиента, а старые записи
  привязаны к ней, только если снимок в записи совпадает с этой машиной —
  запись двухлетней давности на другую машину осталась без ссылки, её
  машина видна из снимка. Обе миграции обратимы: откат возвращает
  основную машину в профиль.

`phone`, `code_hash`, `expires_at`, `used_at`, `attempts`, `request_ip`.

| Группа полей | Что |
|---|---|

| `user`, `service_point`, `oil` | ссылки, `on_delete=PROTECT` |
| `car` | какую машину обслуживали; пусто — машины не было или её удалили из базы |
| `start_at`, `end_at`, `status` | время и статус |
| `client_name`, `client_phone`, `car_model`, `car_plate` | **снимок** данных клиента |
| `oil_title`, `oil_price`, `work_price`, `total_price` | **снимок** позиции и цен |
| `final_price` | итог, если мастер поправил его при расчёте; пусто — итог равен `total_price` |
| `points_spent` | сколько чека закрыто баллами |

| `reminder_sent_at` | защита от повторного напоминания |

**Зачем снимок.** Подорожает масло, клиент сменит машину или имя — история записи
не должна поехать. То, что было согласовано в момент брони, остаётся зафиксированным.

**Статусы:**

```
pending ──┬─→ in_progress ──┬─→ completed
          │                 └─→ cancelled_by_master
          ├─→ completed
          ├─→ cancelled_by_client
          ├─→ cancelled_by_master
          └─→ no_show
```

Разрешённые переходы описаны в `apps/booking/services/booking.py::ALLOWED_TRANSITIONS`.
Всё, чего там нет, — `409 invalid_transition`. Ни один переход не обходит функцию
`_transition`: она пишет историю и рассылает события, забыть её нельзя.

### `booking.BookingPriceChange`

Мастер изменил итог при расчёте: было, стало, причина (необязательна),
кто и когда. Отдельной таблицей, а не строкой в истории статусов: сумма —
это деньги, и спорить о ней будут по числам, а не по тексту комментария.

### `booking.BookingStatusLog`

Кто, когда и с каким комментарием менял статус. Нужен для разбора спорных ситуаций
и для аналитики (сколько отмен, сколько неявок).

### `notifications.Notification`

Журнал всех отправленных сообщений: получатель, тип, текст, статус доставки,
id у провайдера, ошибка. Нужен, чтобы доказать факт предупреждения об отмене,
не отправить одно и то же дважды и посчитать расходы на SMS.

### Два решения, которые стоит понимать

**Слоты не хранятся в базе.** Свободное время вычисляется на лету из графика точки
(`apps/booking/services/slots.py`). Таблица слотов потребовала бы генерации вперёд,
регулярной чистки и синхронизации при каждом изменении графика. Вычисление всегда
согласовано с настройками точки.

**Остаток масла не уменьшается при записи.** Доступность считается как
«физический остаток − активные брони − живые черновики». Списание происходит ровно
один раз — при переводе записи в «Выполнена». Иначе пришлось бы возвращать канистру
при каждой отмене и постоянно ловить рассинхрон.

## Ключевой механизм: черновик записи

Требование заказчика: **как только клиент начал записываться, в системе появляется
объект, по которому в реальном времени видно, на каком он шаге и что уже выбрал.
На всё про всё — 5 минут.**

Это реализовано моделью `BookingDraft`.

### Жизненный цикл

```
POST /bookings/drafts/          →  started            (создан, таймер пошёл)
    select-point                →  point_selected
    select-oil                  →  oil_selected
    select-slot                 →  slot_selected
    confirm                     →  confirmed          → создаётся Booking

в любой момент:
    cancel                      →  cancelled          (клиент прервал)
    таймер вышел                →  expired            (5 минут истекли)
    новый старт с restart=true  →  cancelled          (close_reason=restarted)
```

### Таймер не продлевается на шагах

`expires_at` ставится один раз, при создании: `now + 300 секунд`. Ни один шаг его
не двигает. Иначе слот можно было бы удерживать бесконечно, перещёлкивая масло
туда-сюда.

### Черновик резервирует ресурсы

**Пока черновик жив, он держит и слот, и канистру масла.**

```
свободных постов в слоте = posts_count − активные брони − живые черновики
доступно канистр масла   = остаток на складе − активные брони − живые черновики
```

Поэтому два клиента не выберут последнее свободное время одновременно. Отмена
черновика и истечение таймера освобождают резерв немедленно.

### Истечение проверяется в трёх местах

1. При чтении черновика (`get_open_draft`).
2. На каждом шаге (`_lock_draft`).
3. Celery-задачей `expire_stale_drafts` раз в 20 секунд.

Первые два гарантируют, что «протухший» черновик не оживёт, даже если воркер лежит.
Третье нужно, чтобы слот освободился для **других** клиентов, даже если владелец
черновика просто закрыл приложение.

### Проверки повторяются при подтверждении

Между выбором времени и нажатием «Подтвердить» может пройти четыре минуты. За это
время слот мог занять другой клиент (`409 slot_taken`) или масло могло закончиться
(`409 oil_out_of_stock`). Узнать об этом клиент должен **до** создания записи.

### Защита от гонок

- Строка черновика берётся под `SELECT … FOR UPDATE OF self` — шаги одного клиента
  сериализуются.
- При выборе времени и при подтверждении блокируется строка точки
  (`ServicePoint … FOR UPDATE`) — параллельные подтверждения на одну точку
  выстраиваются в очередь.
- Партиальный уникальный индекс `uniq_open_draft_per_user` — у клиента физически
  не может быть двух живых черновиков.
- Партиальный уникальный индекс `uniq_active_booking_per_user_slot` — один клиент
  не займёт один и тот же слот дважды.

> **Про `OF self`.** `select_for_update()` вместе с `select_related()` по nullable
> внешнему ключу порождает LEFT JOIN, а PostgreSQL отказывается блокировать
> nullable-сторону внешнего соединения (`FOR UPDATE cannot be applied to the
> nullable side of an outer join`). Поэтому блокируется только строка черновика —
> она и есть предмет гонки.

### Повторный старт идемпотентен

`POST /bookings/drafts/` при живом черновике **возвращает существующий**, а не
создаёт новый. Перезагрузка экрана не сбрасывает прогресс и не крадёт время
таймера. Чтобы начать заново намеренно — `{"restart": true}`.

## Аутентификация

Пароля у клиента нет. Вход по одноразовому коду: **сначала звонком**, код —
последние 4 цифры номера, с которого звонят (SMS.RU, метод `/code/call`).
После двух звонков без входа клиенту предлагают **код в SMS**.

```
POST /api/v1/auth/otp/request/   {"phone": "+79001234567", "channel": null | "sms"}
     → {"phone", "expires_at", "resend_after_seconds",
        "channel": "call" | "sms", "sms_available", "debug_code"?}

POST /api/v1/auth/otp/verify/    {"phone": "+79001234567", "code": "4821"}
     → {"access", "refresh", "is_new_user", "user": {...}}
```

Если аккаунта с таким телефоном нет — он создаётся здесь же. Флаг `is_new_user`
подсказывает приложению, что стоит попросить имя.

### Звонок, потом SMS

- **Почему звонок.** Дешевле SMS (0,40 ₽ против рубля с лишним) и не
  требует согласованного буквенного отправителя, без которого SMS не
  уходят вовсе. Ключ у SMS.RU тот же — `SMS_API_KEY`.
- **Код называет шлюз, а не мы**: это хвост номера, с которого он позвонит.
  Поэтому звонок заказывается синхронно, прямо в запросе кода, а не через
  Celery, как SMS: без ответа шлюза нечего сохранить. Два одновременных
  запроса не оплатят два звонка — номер держит короткий замок в кеше.
- **Когда SMS.** Каждый повторный запрос кода значит, что предыдущий звонок
  не помог. После `OTP_CALLS_BEFORE_SMS` (2) таких звонков — за последний
  час и после последнего входа — в ответе `sms_available: true`, и
  следующий код можно попросить с `channel: "sms"`. Раньше — `400
  otp_sms_not_available`. Лимиты общие: пауза 60 секунд и 5 кодов в час на
  номер считают и звонки, и SMS.
- **Шлюз звонков отказал** (нет денег, сбой) — в том же запросе уходит SMS,
  ответ приходит с `channel: "sms"`: войти человек должен, даже когда звонки
  не работают. Сорвавшийся звонок остаётся в журнале уведомлений.
- **Журнал.** Звонок — строка `Notification` с каналом `call`, без кода:
  расходы на вход считаются по журналу, как у SMS. IP клиента уходит в
  шлюз — SMS.RU просит его для защиты от перебора номеров.
- Проверить звонок на сервере, не проходя вход:
  `manage.py send_test_sms +7… --call`.

### Второй режим: обратный звонок VerificaHub

`OTP_MODE=verificahub` — клиент **сам звонит** на номер, который показало
приложение (обратный flash-call VerificaHub, 0,25 ₽), и может сбросить
звонок сразу. Код не вводится: VerificaHub узнаёт клиента по номеру
звонящего. Режим появился потому, что входящий звонок с кодом у части
абонентов не доходил: его глушат антиспам оператора и «заглушение
неизвестных» на телефоне, а исходящий звонок самого клиента — нет.

```
POST /auth/otp/request/      → {"channel": "reverse_call", "number_to_call": "+7909…",
                                "session": "…", "sms_available", …}
POST /auth/otp/call-status/  {"phone", "session", "invite"?}
     → 202 {"status": "pending"}  — звонка ещё нет, спросите через 2 с
     → 200 {access, refresh, …}    — как у otp/verify
     → 410 otp_expired / 400 otp_call_failed — начать заново
```

- **Сессия обязательна.** Кода в этом режиме нет, и знать номер телефона
  мало: статус отдаётся только с `session` из ответа на запрос. Иначе
  кто угодно, знающий номер, опрашивал бы статус и вошёл бы в аккаунт в
  ту секунду, когда звонит его хозяин. В базе — только sha256 сессии.
- **Приложение опрашивает раз в 2 секунды** и сразу — когда возвращается
  на экран из «Телефона». Сбой шлюза (`503 otp_unavailable`) ожидание не
  прерывает. Лимит опроса — `otp_poll`, 400 в час с адреса.
- **Запасное SMS — тоже у VerificaHub** (по решению заказчика), правило
  то же: после двух попыток звонком без входа (`sms_available`). Кода мы
  не знаем и тут — введённый клиентом код проверяет шлюз
  (`/v1/verify/check`), а лимит попыток ввода наш, как и прежде.
- **Шлюз не принял обратный звонок** — сразу SMS; не принял и SMS — `503
  otp_unavailable`: войти сейчас нельзя, и приложение так и говорит.
- **Без ключей** (`VERIFICAHUB_API_KEY`/`SECRET` пусты) работает заглушка:
  номер `+70000000000`, звонок «подтверждается» на втором опросе, код SMS —
  в логе. Для разработки; на проде `security_audit` считает это провалом.
- Режим 1 (`OTP_MODE=smsru`) не менялся. Старые сборки приложения в
  режиме verificahub не умеют показать номер для звонка — нужна новая.

### Сотрудники входят по паролю

Панели `/master/` и `/admin-panel/` — телефон и пароль,
`POST /api/v1/auth/staff/login/`. **Вход кодом на номер сотрудника
закрыт** (`403 staff_use_password` и при запросе кода, и при проверке):
иначе пароль ничего бы не защищал — код звонком получает любой, у кого в
руках телефон мастера.

- Пароль задаёт администратор в Django-админке (`/admin/` → Пользователи);
  тот же пароль, что для самой админки.
- Неверный пароль, клиентский и несуществующий номер — одинаково `400
  invalid_credentials`, и хеш считается даже для несуществующего номера:
  по ответу и по времени ответа список сотрудников не собрать.
- Перебор: `staff_login` 30 запросов в час с адреса (DRF) и блокировка
  номера после `STAFF_LOGIN_MAX_FAILURES` (5) неверных паролей на
  `STAFF_LOGIN_LOCK_MINUTES` (15) — с любого адреса (`429 login_locked`).

### Нормализация телефона

`8 (900) 111-22-33`, `+7 900 111 22 33` и `79001112233` приводятся к одной строке
`+79001112233`. Без этого один человек завёл бы три аккаунта. Используется
библиотека `phonenumbers`, регион по умолчанию — `RU` (настройка `DEFAULT_PHONE_REGION`).

### Защита

| Уровень | Правило | Настройка |
|---|---|---|
| Пауза между отправками | 60 секунд | `OTP_RESEND_COOLDOWN_SECONDS` |
| Лимит на номер | 5 кодов в час | `OTP_MAX_PER_PHONE_PER_HOUR` |
| Попытки ввода | 5, потом код гасится | `OTP_MAX_VERIFY_ATTEMPTS` |
| Время жизни кода | 5 минут | `OTP_TTL_SECONDS` |
| Throttling по IP | DRF ScopedRateThrottle | `DEFAULT_THROTTLE_RATES` |
| Кого считать «одним IP» | последние N элементов `X-Forwarded-For` | `NUM_PROXIES` |

**Про `NUM_PROXIES`.** `X-Forwarded-For` начинает писать сам клиент, а nginx
только дописывает к нему свой `$remote_addr`. По умолчанию DRF берёт
заголовок целиком — то есть ключ throttling оказывается под контролем того,
кто шлёт запрос, и лимит «10 кодов в час на IP» обходится одной лишней
строкой в запросе. Настройка говорит, сколько элементов с конца
принадлежат своим прокси: `0` — приложение смотрит в сеть напрямую,
`1` — за одним nginx (значение по умолчанию в `settings/prod.py`).
Ошибка в другую сторону тоже заметна: при `0` за nginx у всех клиентов
`REMOTE_ADDR` равен `127.0.0.1`, и лимит на один адрес становится лимитом
на весь сайт.

Новый запрос кода гасит предыдущий — рабочим остаётся только последний.
Код используется один раз (`used_at`), повторная проверка даёт ошибку.

### JWT

`access` живёт 60 минут, `refresh` — 30 дней, с ротацией и чёрным списком
(`ROTATE_REFRESH_TOKENS`, `BLACKLIST_AFTER_ROTATION`). Обновление —
`POST /api/v1/auth/token/refresh/`. Заголовок: `Authorization: Bearer <access>`.

| PATCH, DELETE | `/garage/journal/{id}/` | своя запись дневника; замены у нас не правятся |

### Дневник водителя («Гараж»)

`garage.LogEntry` — запись по машине: заправка, замена масла, ТО и
ремонт, шиномонтаж, мойка, штраф, другое. Считает всё
`garage/services/journal.py` при чтении — записей у машины сотни, и
пересчёт дешевле, чем следить за сохранёнными итогами.

- **Замены масла у нас в дневник не копируются**: они берутся из
  выполненных записей на эту машину, сумма — сколько заплачено деньгами.
  Копия разошлась бы с записью, когда мастер поправит итог.
- **Расход — от полного бака до полного.** Неполная заправка добавляет
  литры к отрезку, но сама его не закрывает; средний — по всем отрезкам.
- **Пробег машины** — наибольший известный: из карточки и из дневника.
  Пробег при замене у нас (в записи на сервис его нет) берётся с
  ближайшей записи дневника не дальше 14 дней.
- **Напоминания** (без push и SMS — внутри приложения, решение заказчика):
  масло — по умолчанию каждые `GARAGE_OIL_INTERVAL_KM` (10 000) км или
  `GARAGE_OIL_INTERVAL_MONTHS` (12) месяцев, что раньше, у машины можно
  задать свой интервал; ОСАГО и техосмотр — по датам машины; резина — с
  `GARAGE_SUMMER_TIRES_FROM` (20.04) на летнюю и `GARAGE_WINTER_TIRES_FROM`
  (01.10) на зимнюю, за `GARAGE_SOON_DAYS` до даты и месяц после, пока нет
  записи «Шиномонтаж». «Скоро» — за `GARAGE_SOON_KM` (1000) км или
  `GARAGE_SOON_DAYS` (30) дней.
- **Статистика** — календарный месяц и год: сумма по категориям, пробег
  за период, средний расход.

Поле `can_cancel` в ответе показывает, доступна ли отмена прямо сейчас — чтобы
приложение не показывало кнопку, которая вернёт `409`. `can_reschedule` — то
же для переноса.

**Перенос** разрешён ровно тогда, когда отмена: запись в ожидании и до
визита больше `BOOKING_CANCEL_DEADLINE_MINUTES` — перенос и есть отмена
старого времени, пост под клиента к этому моменту уже готовят. Новое время
проверяется как при записи (`validate_slot` под блокировкой строки точки),
масло остаётся обещанным той же записи, статус не меняется; в историю
пишется «Перенесена клиентом с … на …», напоминание отправится заново — к
новому времени, мастеру уходит сигнал в канал.

**Цен в клиентском API нет** (решение заказчика): ни у масел
(`/service-points/{id}/oils/`, масло в черновике), ни у записей — ни цены
масла, ни работы, ни суммы записи. Убраны из ответа, а не только из
вёрстки: спрятанное в интерфейсе, но лежащее в JSON — та же публикация.
У выполненной записи есть `final_price` (итог, который клиент заплатил) и
`paid_amount` (деньгами); до выполнения оба `null`. В истории баллов нет
базы и ставки начисления: база — сумма чужого чека. Мастер и
администратор видят цены, как раньше, — у них свои сериализаторы.

Машина в записи — `car` (`id`, `title`, `plate`) и снимок `car_model`,
`car_plate`: показывать стоит снимок, машину могли переименовать.

### Запись клиента мастером

Клиент позвонил или приехал без записи — мастер записывает его сам: кнопка
«Записать клиента» над списком в `/master/`, на сервере
`POST /master/bookings/`, логика — `apps/booking/services/walk_in.py`.

- **Проверки те же, что у записи из приложения, и из тех же модулей**
  (`slots.validate_slot`, `stock.get_available_oil`): свободный пост с
  учётом живых черновиков, масло на полке, горизонт записи, нет ли у
  клиента другой записи на это время. Точка берётся под ту же блокировку
  строки, что и при подтверждении черновика, — последний пост не
  достанется двоим, откуда бы они ни записывались.
- **Живая очередь.** Минимального запаса до начала у мастера нет: можно
  записать и в слот, который уже идёт, если пост свободен. Закончившийся
  слот — `slot_too_soon`.
- **Клиента по номеру.** Есть — имя подставляется, а машины клиента
  появляются кнопками, основная выбрана; выбранная уходит как `car_id`.
  Мастер может вписать другую машину — сервер найдёт её среди машин
  клиента по номеру (`a123bc` и `А123ВС` — один номер), без номера — по
  названию, а не найдёт — добавит в гараж клиента второй, не основной.
  Существующие машины и имя мастер не переписывает: клиент мог поправить
  их сам. Нет аккаунта — он заводится таким же, как при входе по SMS: без
  пароля, сразу с узлом в реферальной программе и с названной машиной.
  Потом человек входит в приложение по этому номеру и видит запись.
  Номер сотрудника — `phone_is_staff`.
- **Снимок в записи — то, что ввёл мастер.** В истории статусов —
  «Запись создана мастером» и его имя. Клиенту уходит то же SMS
  «запись создана», что и при записи из приложения (выключается тем же
  `SMS_ENABLED_KINDS`).
- **Без черновика.** Пятиминутный таймер держит слот, пока клиент думает
  в приложении, а мастер вводит всё одним окном и подтверждает сразу.
  Общий конец обоих путей — `booking.create_booking`: снимок, история,
  событие в канал и SMS.
- **Права:** роль `master`/`admin`; мастер с заданными `service_points`
  записывает только на свои точки (`point_not_allowed`).

### Метрики администратора

`GET /master/metrics/?date_from=YYYY-MM-DD&date_to=YYYY-MM-DD&service_point=<uuid>`

Мастеру этот эндпоинт закрыт: `403 permission_denied`. Выручка сети, воронка и
остатки — не то, что нужно человеку у подъёмника, поэтому права проверяет
отдельный `IsAdmin`, а не общий `IsMaster`.

Период по умолчанию — последние 30 дней. Сутки считаются в часовом поясе сети
(`BUSINESS_TIMEZONE`), а при фильтре по точке — в её собственном поясе.

Один ответ закрывает весь экран, чтобы панель не склеивала полдюжины запросов:

| Блок | Что внутри |
|---|---|
| `totals` | записи по статусам, выручка (масло + работа), средний чек, доли отмен и неявок |
| `funnel` | глубина черновиков по шагам, причины закрытия, конверсия в запись |
| `by_day` | динамика по дням; дни без записей приходят нулями, чтобы график не врал |
| `by_hour` | загрузка по часам суток |
| `by_point` | сравнение адресов по записям и выручке |
| `top_oils` | ходовые позиции масла |
| `clients` | всего клиентов, новые за период, возвращавшиеся |
| `stock` | остатки канистр с флагом `is_low` |
| `live` | живые черновики и предстоящие записи прямо сейчас |

**Глубина воронки считается по заполненным полям черновика, а не по его шагу.**
Шаг закрытого черновика перезаписывается на `expired`/`cancelled`, и информация
о том, докуда дошёл клиент, из него теряется. А `service_point`, `oil` и
`slot_start` остаются как есть — по ним и видно, где человек остановился.

Расчёт живёт в `apps/master/metrics.py`, вьюха только разбирает фильтры: правило
тонких вьюх действует и здесь.

### Реферальная программа

Клиент приводит знакомых по своему коду и получает баллы с их чеков.
Баллы — скидка на следующую замену (1 балл = 1 ₽), не деньги.

### Схема: бинарное дерево, выплата раз в сутки

Под каждым участником **два места** — левое и правое плечо. Приглашённый
встаёт на первое свободное место в ветке пригласившего (обход в ширину,
сначала левое), так что дерево заполняется уровень за уровнем — и при
переполнении человек падает ниже (спиловер).

**1. Баллы в плечо.** Когда мастер отмечает запись выполненной, заплаченное
деньгами превращается в баллы для трёх вышестоящих — по ставкам линий
`REFERRAL_LEVEL_PERCENTS` (по умолчанию 5 %, 4 %, 3 %). Баллы ложатся **не на
баланс, а в плечо** вышестоящего — в то, где стоит покупатель
(`LegCredit`).

| Линия под участником | Ставка | Мест максимум |
|---|---|---|
| 1 — прямо под ним | 5 % | 2 |
| 2 | 4 % | 4 |
| 3 | 3 % | 8 |

**2. Сведение в 00:00 по Челябинску** (`REFERRAL_PAYOUT_TIMEZONE`,
Asia/Yekaterinburg). К остатку прошлых суток прибавляется пришедшее за
день, и плечи сравниваются:

| Слева | Справа | Выплата | Переносится |
|---|---|---|---|
| 300 | 0 | 0 — одно плечо пустое | слева 300 |
| 300 | 300 | 600 — равны, выплачиваются оба | ничего |
| 300 | 500 | 300 — меньшее плечо | справа 200 |

Излишек сильного плеча ждёт, пока слабое его догонит. Выплата — строка
журнала `PAYOUT` и прибавка к балансу; вся арифметика суток лежит в
`BinarySettlement` (что было, что пришло, что выплачено, что осталось) —
ответ на «почему мне заплатили 300, а не 600».

Правила — от заказчика, и на полном дереве расчёт совпадает с его
таблицей (`МОЙ_СЕРВИС.xlsx`): при чеке 6000 ₽ участник с заполненными
тремя линиями получает 600 + 960 + 1440 = **3000 баллов**
(`test_full_tree_pays_exactly_like_the_spreadsheet`).

**Почему задача раз в 5 минут, а не ровно в полночь.** Она сводит все
сутки, которые уже закончились и ещё не сведены, — по одним, по порядку.
Выплата приходит в первые минуты после полуночи, а если воркер лежал всю
ночь, пропущенные сутки догоняются каждые отдельно: при переносе остатка
три дня, слитые в один, дали бы другую сумму.

### Списание при расчёте

При завершении записи мастер в окне «Расчёт» видит чек, баланс клиента и
сколько можно списать — не больше `REFERRAL_MAX_DISCOUNT_PERCENT` (50 %)
от чека. Сколько списать, решает клиент. Списание, завершение записи,
списание канистры и баллы в плечи вышестоящих — **одна транзакция**:
ошибка в любом месте откатывает всё.

- Часть чека, закрытая баллами, **новых баллов не рождает**: база — то, что
  заплачено деньгами (`REFERRAL_BASE=total`). Иначе баллы воспроизводили бы
  сами себя.
- **Выручка** в сводке мастера и в метриках — тоже деньгами; сколько
  закрыто баллами, показано рядом.

### Итог при расчёте

Мастер может изменить итог в окне «Расчёт» — долил масла, добавил работу
или уступил. И вверх, и вниз, без предела, причина необязательна (так
решил заказчик); итог больше нуля.

- **Итог хранится отдельно от снимка цены** (`Booking.final_price`):
  `total_price` остаётся ценой на момент записи, по ней видно, откуда
  взялась разница. Кто, когда, с чего на что и почему — в
  `BookingPriceChange` и строкой в истории статусов.
- **От итога считается всё денежное:** потолок оплаты баллами (50 % от
  итога), баллы в плечи (заплаченное деньгами — итог минус баллы),
  выручка в сводке мастера и в метриках, средний чек, сумма в SMS
  «работы выполнены». В метриках масло и работа остаются по ценам записи,
  а правки идут отдельной строкой `adjustments`: доплату за долитое масло
  ни к маслу, ни к работе честно не отнести. По той же причине при
  `REFERRAL_BASE=work` правка в базу баллов не попадает.
- **Порядок в транзакции:** сначала итог, потом списание баллов — потолок
  проверяется уже от нового итога. Ошибка в любом месте откатывает всё,
  включая итог и строку журнала.
- **Клиент видит итог** в «Моих записях» (Android и iPhone) — только у
  выполненной записи: `final_price` и `paid_amount`, до выполнения `null`.
  Цену записи, по которой видно «было N», клиенту не отдаём (цен клиент
  не видит вовсе, см. «Мои записи» в справочнике API). SMS «работы
  выполнены» с суммой осталось — по решению заказчика.

### Сколько это стоит сервису

С каждого чека вверх уходит до 5 + 4 + 3 = **12 %** — но только когда у
получателя сошлись оба плеча. Неравные плечи платят по меньшему, остаток
ждёт, поэтому фактическая нагрузка ниже 12 %. `REFERRAL_BASE=work` считает
процент от работы, а не от полного чека: масло перепродаётся с почти
фиксированной наценкой, и дорогая канистра увеличивала бы выплату, не
увеличивая заработок.

### Что защищено

- **Двойное «Выполнено».** Уникальный индекс `uniq_credit_per_booking_node`:
  одна запись даёт вышестоящему одно поступление.
- **Двойная выплата.** `uniq_settlement_per_day`: сутки участника сводятся
  один раз, даже если задачу запустили дважды.
- **Гонка за место в дереве** — `uniq_matrix_slot`, поиск повторяется.
- **Кольцо в дереве, самоприглашение, смена пригласившего** — отказ.
- **Изменение ставок задним числом.** В каждом поступлении — снимок ставки
  и базы.
- **Уход баланса в минус** — списание под блокировкой строки узла.
- **Обход потолка двумя списаниями** — потолок считается на весь чек.

### Модели

- **`ReferralNode`** — место в дереве: `sponsor` (кто пригласил), `parent`
  (под кем стоит), `position`, `depth`, `balance`, `carry_left`,
  `carry_right` (невыплаченный остаток плеч).
- **`LegCredit`** — баллы в плечо с чужой покупки до сведения.
- **`BinarySettlement`** — сведение плеч участника за сутки.
- **`PointsEntry`** — журнал движений баллов: `payout` (выплата), `spend`
  (списание), `adjustment`; `accrual` — начисления прежней схемы «сразу три
  линии вверх», новые не создаются, старые остаются в истории.

### Настройки

```bash
REFERRAL_ENABLED=true
REFERRAL_LEVEL_PERCENTS=5,4,3              # длина списка задаёт глубину
REFERRAL_BASE=total                        # total (деньгами) | work
REFERRAL_WIDTH=2                           # два плеча
REFERRAL_MAX_DISCOUNT_PERCENT=50           # потолок оплаты баллами
REFERRAL_PAYOUT_TIMEZONE=Asia/Yekaterinburg  # полночь выплат — по Челябинску
```

### Приглашение без ручного ввода

Ссылка `/i/<код>` и QR-код — один и тот же адрес. Что происходит дальше —
по сценариям и платформам (проверено: Android — в эмуляторе на оболочке
2.0, iPhone — в браузере с подменой; на живых устройствах не проверялось):

| Сценарий | Android | iPhone |
|---|---|---|
| Приложения нет, открыл ссылку | Страница → «Google Play» со ссылкой `referrer=invite=<код>` → после установки оболочка забирает код через Install Referrer → он уходит вместе со входом | Страница → «Установить приложение» (`/app/?install=1&invite=<код>`) → код попадает в `start_url` манифеста → приложение с экрана «Домой» открывается уже с кодом → он уходит вместе со входом |
| Приложение стоит, открыл ссылку | **Только при заполненном `ANDROID_CERT_FINGERPRINTS`**: App Links открывают оболочку, код откладывается, вошедший привязывается сразу. Пока отпечатка нет — открывается страница, как без приложения: «Скопировать код» → в приложении «Вставить код» | Веб-приложение с главного экрана **ссылки из Safari не перехватывает** — это ограничение iOS, обойти его без App Store нельзя. Страница так и пишет: «Скопировать код» → открыть приложение → «Вставить код» (одно нажатие, iOS покажет системное «Вставить») |
| Друг рядом | «Сканировать QR» на входе или в «Бонусах» (камера в оболочке) | То же (jsQR) |
| Пришло сообщение со ссылкой | Скопировать сообщение целиком → «Вставить код»: разбор находит код в ссылке | То же |
| Открыл ссылку на компьютере | Страница с кодом и обеими кнопками установки | То же |

Дальше код уходит на сервер **вместе со входом** (`invite` в
`POST /auth/otp/verify/` и в `POST /auth/otp/call-status/` для обратного
звонка), и сервер привязывает человека сразу (`accounts.services.apply_invite`);
ответ несёт `invite.status` и имя пригласившего. Уже вошедший клиент с
отложенным кодом привязывается при открытии приложения. Отказ («уже
принято», неверный код) вход не ломает, а «уже принято» и вовсе молчит —
человек просто второй раз открыл ссылку.

**Что нужно, чтобы на Android ссылка открывала приложение:** SHA-256
отпечаток ключа подписи из Play Console (Play App Signing) — в
`ANDROID_CERT_FINGERPRINTS` на сервере. Без него `/.well-known/assetlinks.json`
отдаёт 404, и система открывает ссылку в браузере.

### Что видит клиент

Экран «Бонусы» (макет «одна цифра», выбран по дизайну): крупно — сколько
баллов можно потратить, одной строкой — что придёт ближайшей ночью, одна
главная кнопка «Пригласить друга» (системное «Поделиться»), рядом код и
QR. Свёрнуто вторым уровнем: история баллов, приглашённые, «Как
начисляются баллы» (плечи названы ветками) и «У меня есть код
приглашения» — ввод, «Вставить код», сканер. Узел в дереве заводится при регистрации; тем, кто
зарегистрировался раньше, — `manage.py backfill_referral_nodes`.
Сотрудникам узел не заводится: сервис не начисляет баллы сам себе.

### Чего ещё нет

- дерева и журнала выплат в панели администратора — пока Django-админка
  (`LegCredit`, `BinarySettlement` там есть, только чтение).

## Справочник автомобилей

У машины в гараже «марка и модель» — свободная строка. Справочник (73 марки,
545 моделей) нужен для подсказок при её заполнении, а не для ограничения:
редкую или новую машину клиент впишет сам. Упереться в неполноту нашего
списка прямо на регистрации — это потерянный клиент, а справочник
автомобилей полным не бывает никогда.

**Поиск находит машину как её ни набери:** «мерс», «merc», «Мерседес»,
«мерседес бенц», «кия рио», «kia rio», «камри», «camry». Работает это без
полнотекстового индекса и без `pg_trgm`: и запрос, и справочник приводятся
к одной форме — латиница без разделителей (`apps/common/translit.py`), —
после чего хватает обычных `startswith` и `contains`. Проект не должен
зависеть от того, с какими расширениями собран PostgreSQL.

Три правила выросли из прогона по живым данным, а не из головы:

1. **Совпадение только с начала слова.** Простой `contains` по «рио» выдавал
   UAZ: внутри «patriot» сидит «rio». Человек набирает начало слова, а не
   его середину.
2. **Слова запроса ищутся по отдельности и все сразу.** «киа рио» после
   нормализации склеивалось в «kiario» и не находило ничего. Порядок слов
   при этом не важен — «рио киа» тоже работает.
3. **Синонимы марки входят в индекс её моделей.** Иначе «кия рио» работало
   бы, а «кия» — нет.

**Чего поиск не умеет:** прощать опечатки и склонения. «вест» находит Lada
Vesta, «весту» — уже нет. Лечится триграммами в PostgreSQL, но браться за
это стоит, когда станет видно, что люди действительно промахиваются, а не
заранее.

Справочник лежит текстом — [`apps/catalog/data/cars.txt`](apps/catalog/data/cars.txt),
по строке на марку:

```
LADA | Лада, ВАЗ, Жигули | Granta, Vesta, Largus, Niva Legend, XRAY, …
```

Порядок строк задаёт порядок в списке, когда клиент открыл выбор и ничего
не набрал: сверху то, что реально заезжает на замену, а не то, что раньше
по алфавиту. Транслитерацию в синонимах писать не нужно, её делает код.

Загрузка и обновление:

```bash
docker compose … exec api python manage.py import_cars
```

Повторный запуск безопасен: существующие записи обновляются, ничего не
удаляется. Снятые с продажи марки убираются галочкой `is_active` в админке —
удалять их не стоит: на них ссылаются машины клиентов (ссылка обнулится,
название машины останется).

Текстом, а не фикстурой и не миграцией данных, по двум причинам: файл
правит человек, которому не нужно знать ни JSON, ни Django, и он будет
пополняться — новые марки появляются каждый год, а миграция данных,
которую переписывают, перестаёт быть миграцией.

## Уведомления и SMS

| Событие | Текст |
|---|---|
| Код входа | `Код для входа: 4821. Никому его не сообщайте.` |
| Запись создана | адрес, время, масло, код записи |
| Напоминание | за 2 часа до визита |
| Отмена сервисом | с причиной, которую указал мастер |
| Работы выполнены | сумма |

Тексты собраны в одном месте — `apps/notifications/templates.py`. Формулировки
читает клиент, и правят их не программисты.

Отправка **всегда асинхронная**, через Celery: подтверждение записи не должно ждать
SMS-шлюз, а падение шлюза не должно откатывать бронь. Задача ставится в очередь
через `transaction.on_commit` — то есть только после того, как запись реально
попала в базу.

Все отправки логируются в `Notification`. **Текст кода входа в журнале
замаскирован** (`Код для входа: ****`) — сам код в базу не попадает.

### Подключение реального шлюза

`SMS_PROVIDER=console` (по умолчанию) печатает сообщения в лог воркера —
этого достаточно для разработки. Для боевой отправки подключён SMS.RU:

```bash
SMS_PROVIDER=smsru
SMS_API_KEY=<api_id из личного кабинета>
SMS_SENDER=<зарегистрированный буквенный отправитель>
```

**Бесплатной боевой отправки SMS не существует.** Бесплатны только тестовые
сообщения, которые шлюзы дарят при регистрации — их хватает, чтобы
проверить подключение, и не хватает ни на что больше. Всё остальное
оплачивается за сообщение.

Порядок подключения:

1. Зарегистрироваться на sms.ru, подтвердить свой номер.
2. Забрать `api_id` в личном кабинете (раздел «Программистам» → API).
3. Прописать его в `.env` на сервере и перезапустить контейнеры:
   `docker compose … up -d` (именно `up -d`, а не `restart` — `env_file`
   перечитывается только при пересоздании).
4. **Зарегистрировать буквенного отправителя** — https://sms.ru/?panel=senders
   Без него шлюз не пропускает ни одного сообщения и отвечает кодом 221.
   Это требование операторов, а не конкретного шлюза: отправка с общего
   номера в России закрыта, и сменой провайдера это не обходится. Имя
   должно соответствовать домену, названию юрлица или товарному знаку,
   проходит модерацию. Пока модерация не пройдена, отправки не будет
   вообще — планируйте этот шаг заранее.
   **Имя должно совпадать с доменом по написанию.** Основной домен —
   `moi-servis.ru`, поэтому подавать стоит `MOISERVIS` (дефис в имени
   отправителя не нужен).
   Домены прошлого бренда (`ekspres-zamena.ru`, `экспрес-замена.рф`)
   формально тоже годятся как основание, но написаны с одной «с» и в SMS
   читаются как опечатка. `MOISERVIS` совпадает и с доменом, и с названием
   компании — подавать нужно его.
5. Прописать одобренное имя в `SMS_SENDER` и снова пересоздать контейнеры.
6. Проверить отправку, не проходя весь вход:
   ```bash
   docker compose … exec api python manage.py send_test_sms +79001234567
   ```
   Команда шлёт сообщение синхронно, мимо Celery, и печатает ответ шлюза
   целиком — ошибка ключа видна сразу, а не в логах воркера. На провайдере
   `console` она предупреждает, что сообщение никуда не ушло: «Отправлено»
   в логе выглядит как успех, и перепутать легко.

Сменить шлюз — это соседний класс рядом с `providers/smsru.py` и строка в
`.env`. У SMSC, SMS Aero и P1SMS API устроены так же: POST с ключом и
разбор JSON. Прикладной код не меняется, он работает через `SmsProvider`.

### Временные и постоянные ошибки

Шлюз отвечает двумя уровнями статусов: общим на запрос и отдельным на
каждый номер. Неверный ключ виден в первом, недоступный номер — только во
втором, поэтому разбираются оба.

| Класс ошибки | Исключение | Что делает система |
|---|---|---|
| шлюз не ответил, таймаут, HTTP 5xx, не-JSON | `SmsDeliveryError` | 5 повторов Celery с нарастающей паузой |
| неверный ключ, нет денег, не зарегистрирован отправитель, номер в стоп-листе | `SmsRejectedError` | помечает уведомление неудачным и останавливается |

Разделение нужно, чтобы не крутить пять повторов подряд там, где чинить
надо настройки, а не ждать. Список постоянных кодов — в `PERMANENT_CODES`
в `providers/smsru.py`.

Остаток на счету приходит в каждом ответе шлюза и пишется в лог: это
бесплатный способ узнать, что деньги кончаются, до того как отправка
встанет.

### Как платить меньше

Основной расход — не коды входа, а сопровождение записи. На одну бронь
сейчас приходится три SMS (создана, напоминание, выполнена) плюс код входа.

`SMS_ENABLED_KINDS` перечисляет типы, которые реально уходят. Всё, что не
попало в список, остаётся в журнале со статусом «Не отправляли»: тихо
выбрасывать запись нельзя, «клиенту не сообщили» — такой же факт, как
«сообщили», и он должен быть виден.

Разумный минимум:

```bash
SMS_ENABLED_KINDS=otp,booking_reminder,booking_cancelled_by_master
```

- **код входа** — без него нельзя войти;
- **напоминание за 2 часа** — окупается снижением неявок;
- **отмена сервисом** — клиент обязан узнать, что его визит отменили.

Отключаются «запись создана» и «работы выполнены»: и то, и другое клиент
видит в приложении в момент действия. Это убирает две SMS из трёх на
каждую бронь.

Что ещё снижает расходы:

- **Звонок-подтверждение вместо SMS** для кодов входа: клиенту звонят, код —
  последние цифры номера звонящего. У тех же операторов он стоит заметно
  дешевле SMS. Потребует отдельного провайдера рядом с `smsru.py`.
- **Push вместо SMS** для сопровождения записи. В модели `Notification`
  канал `push` уже предусмотрен, отправка не реализована.
- **Лимиты OTP** уже стоят и экономят на переборе: пауза 60 секунд между
  отправками и 5 кодов на номер в час.

## Фоновые задачи

| Задача | Период | Зачем |
|---|---|---|
| `expire_stale_drafts` | 20 секунд | освободить слот брошенного черновика |
| `send_booking_reminders` | 5 минут | SMS за 2 часа до визита, ровно один раз |
| `purge_old_drafts` | сутки | удалить мёртвые черновики старше 7 дней |
| `purge_expired_otp` | час | почистить использованные коды |

Расписание — `CELERY_BEAT_SCHEDULE` в `config/settings/base.py`.

Напоминание защищено от дублей: задача сначала «занимает» запись
условным `UPDATE … WHERE reminder_sent_at IS NULL`, и только потом шлёт SMS.
Повторный запуск задачи не отправит второе сообщение.

Свежие закрытые черновики намеренно не удаляются сразу — по ним видно, на каком
шаге люди отваливаются.

## Конфигурация

Все настройки читаются из `.env` через `django-environ`. Шаблон — `.env.example`.

### Бизнес-правила

Собраны в `settings.BOOKING` и `settings.OTP` — единая точка правды. Меняются без
правок кода:

```bash
BOOKING_DRAFT_TTL_SECONDS=300        # жизнь черновика (требование: 5 минут)
BOOKING_MIN_LEAD_MINUTES=30          # нельзя записаться «через минуту»
BOOKING_HORIZON_DAYS=14              # на сколько дней вперёд открыта запись
BOOKING_CANCEL_DEADLINE_MINUTES=60   # до какого момента клиент отменяет сам
BOOKING_REMINDER_LEAD_MINUTES=120    # за сколько минут напоминать
BOOKING_DRAFT_PURGE_AFTER_DAYS=7     # когда физически удалять мёртвые черновики

OTP_TTL_SECONDS=300
OTP_RESEND_COOLDOWN_SECONDS=60
OTP_MAX_VERIFY_ATTEMPTS=5
OTP_MAX_PER_PHONE_PER_HOUR=5
OTP_DEBUG_EXPOSE_CODE=True           # ⚠ в проде обязательно False
```

### Контакты компании

Всё, что показывает лендинг, кроме цен и адресов, задаётся в `.env`:

```bash
COMPANY_NAME=Мой Сервис
COMPANY_TAGLINE=Замена масла по записи
COMPANY_PHONE=+7 (499) 123-45-67
COMPANY_EMAIL=hello@example.com
COMPANY_WORKING_HOURS=Ежедневно 09:00–21:00
COMPANY_APP_STORE_URL=           # пусто = кнопка «скоро», без перехода
COMPANY_GOOGLE_PLAY_URL=
COMPANY_YEARS_ON_MARKET=0       # 0 = цифру в шапке не показываем
COMPANY_CARS_SERVED=0
COMPANY_RATING=                 # например 4.9; пусто = не показываем
COMPANY_RATING_SOURCE=          # «Яндекс Картах» → «оценка на Яндекс Картах»
```

Цифры в шапке витрины по умолчанию выключены. Раньше в коде стояли
«8 лет», «14 000 машин» и зашитая в шаблон «оценка 4,9», хотя отзывов
система не собирает: забытая переменная выводила на живой сайт
выдуманные числа. Теперь каждая цифра появляется, только когда её
задали, а оценка — только с источником.

Длительности замены на витрине намеренно нет. Обещание «за N минут» —
это то, что клиент проверит секундомером в первый же визит, а замена
зависит от машины: слить отработку с прогретого мотора и с холодного —
разное время. Витрина обещает своё время приезда и отсутствие очереди,
а не скорость работы.

Ассортимент и адреса на лендинг попадают из базы (`Oil`, `ServicePoint`) — там же,
откуда их берёт API. Цен на лендинге нет.

### Эксплуатация

```bash
NUM_PROXIES=0           # сколько своих обратных прокси впереди; за nginx — 1
SENTRY_DSN=             # пусто — ошибки видны только в логах
SECURE_SSL_REDIRECT=True

BACKUP_DIR=backups      # относительно корня проекта
BACKUP_KEEP_DAYS=14
BACKUP_MAX_AGE_HOURS=36 # старше — security_audit считает снимки протухшими
BACKUP_REMOTE=          # цель rsync за пределами сервера
```

Подробности про `NUM_PROXIES` — в разделе «Аутентификация», про бэкапы —
в «Бэкапы PostgreSQL».

### Часовые пояса

В базе **всё в UTC** (`TIME_ZONE = "UTC"`, `USE_TZ = True`). Локальное время берётся
из `ServicePoint.timezone` для каждой точки отдельно. `BUSINESS_TIMEZONE` — пояс,
в котором сотрудники думают о «сегодня», используется в сводке за день.

Вторая точка в другом регионе ничего не сломает.

## Веб-интерфейс

Чистые HTML, CSS и JavaScript — без сборщика, фреймворков и внешних зависимостей.

| Адрес | Кому | Что там |
|---|---|---|
| `/` | клиенту | лендинг: о компании, ассортимент масел (без цен), адреса, ссылки на приложения, телефон для записи |
| `/master/` | мастеру | смена в реальном времени: сводка, фильтры, действия, живые черновики |
| `/admin-panel/` | администратору | всё то же плюс вкладка метрик |
| `/app/` | клиенту на iPhone и в Android-оболочке | веб-приложение: вход, записи (ближайшая, «Записаться», история), гараж (машины и дневник водителя), бонусы, профиль — на iPhone ставится на главный экран, на Android открывается в приложении |

`/admin-panel/`, а не `/admin/`: последний занят Django-админкой, и она остаётся
инструментом для правки справочников.

### Веб-приложение для iPhone (`/app/`)

В App Store приложения нет (нужен Mac и аккаунт Apple Developer), поэтому
iPhone получает веб-приложение: Safari → «Поделиться» → «На экран
„Домой“», дальше оно открывается с иконкой и без рамки браузера. Эти же
экраны открывает Android-приложение — оно оболочка над `/app/` (см.
«Мобильное приложение»), так что веб-приложение — единственный клиент.

- **Preact + htm без сборщика.** Один файл библиотеки (~13 КБ) лежит в
  `static/web/app/vendor/`; Node и сборка в Docker не нужны. Клиент API,
  обновление токена, уведомления и модалки — из того же `core.js`, что у
  панелей сотрудников.
- **Модули подключаются картой импорта** с адресами из `{% static %}`
  (`ClientAppView`, список в `APP_MODULES`). Относительный импорт ушёл бы
  на имя без хеша, а nginx отдаёт `/static/` с годовым `immutable` —
  обновление не доехало бы до телефона. Новый модуль — строка в
  `APP_MODULES`.
- **Service worker** (`/app/sw.js`, шаблон `web/app_sw.js`) кеширует
  оболочку и статику, чтобы приложение открывалось мгновенно; API не
  кеширует никогда. Версия кеша — хеш адресов файлов, то есть меняется с
  каждой выкаткой.
- **Вкладка «Записи»** (`app/bookings.js`) — одна вместо прежних «Запись»
  и «Мои записи»: сверху ближайшая запись крупно с действиями (маршрут в
  Яндекс Картах, позвонить на точку, перенести, отменить), под ней
  «Записаться», ниже история. Мастер записи (`app/booking.js`) открывается
  окном поверх (`Sheet` в `app/lib.js`); черновик живёт на сервере, поэтому
  закрытое окно и другая вкладка его не теряют — вкладка показывает
  «Продолжить запись» с таймером. Выбор времени (`SlotPicker`) общий для
  записи и переноса.
- **Гараж** (`app/garage.js`): машины (переключатель, настройки,
  напоминания по машине), что пора сделать, «+ Добавить запись» — тип
  касанием, пробег подставлен последний известный, — расходы за месяц и
  год, средний расход, последние записи и весь дневник. Напоминание о
  масле ведёт в мастер записи (`startBooking` в `app/lib.js`).
- **Машины** (`app/cars.js`): форма машины и выбор машины на подтверждении
  записи — кнопками, основная выбрана, новую можно добавить тут же.
- **Оформление** — та же неоновая тема, что у витрины (`web/app/app.css`),
  компоненты — из `app.css`. Отступы под системные панели —
  `--safe-top`/`--safe-bottom`: на iPhone из `env(safe-area-inset-*)`, в
  Android-оболочке — от неё (`--native-safe-*`). Иконки главного экрана — PNG из контура фирменного знака
  (`web/app/icons/`), Safari не берёт SVG.
- **Приглашения.** Код из ссылки уходит в `start_url` манифеста и на
  сервер вместе со входом — см. «Приглашение без ручного ввода». Сканер
  QR (`app/scan.js`) грузит распознаватель jsQR (~250 КБ) только при
  открытии.
- **Только iPhone и только с главного экрана** (`app/install.js`), плюс
  Android-оболочка. Android в браузере на `/app/` видит кнопку Google Play (с кодом приглашения),
  компьютер — QR-код, чтобы открыть страницу на iPhone. В Safari на iPhone
  входа нет — только инструкция «Поделиться → На экран „Домой“»:
  у приложения с главного экрана своё хранилище, и вход из Safari туда не
  переехал бы. Код приглашения при этом не теряется — он уже в
  `start_url` манифеста. В разработке (`DEBUG`) из браузера пускает,
  иначе экраны не проверить без телефона; iPhone на компьютере
  эмулируется в инструментах разработчика браузера.
- **Установка под устройство на сайте.** Устройство определяется по
  строке браузера (`web.views.install_links`): iPhone видит только
  «Установить приложение», Android — только Google Play, компьютер — оба.
- **Ограничения iPhone:** push-уведомления работают только у
  установленного приложения (iOS 16.4+) — их отправка на сервере ещё не
  сделана.

### Дизайн-система

**Один источник для веба и Android — `design/`.** `design/tokens.json`
(шкалы и цвета клиентской темы) и `design/mark.svg` (силуэт знака из
`_logo.html`) собираются командой `python design/build.py`: она переписывает
помеченные блоки `design-tokens` в `app.css` (шкалы) и `web/app/app.css`
(цвета клиента), ресурсы Android (`colors.xml`, `dimens.xml`, векторный знак
и монохромную иконку) и рисует иконки — iPhone (`apple-touch-icon`, иконки
манифеста, маскируемая) и Android (адаптивная: фон и знак слоями, знак
шириной 62 из 108 dp — внутри видимого круга при любой маске; квадратная и
круглая для Android 7; заставка Android 12+). Свечение неона — размытые
слои, как `drop-shadow` знака на витрине; иконкам нужен Pillow, проекту —
нет. Сгенерированное руками не правится: `tests/test_design_tokens.py`
сверяет файлы с источником, и CI упадёт, если их поправили мимо него или
забыли пересобрать.

Шкалы заданы один раз в `:root` файла `app.css` и общие для витрины и панелей.
**Значение вне шкалы в CSS не пишется** — нужен новый размер, значит, сначала
решение, что шкала неполна, и новая ступень в `:root`. Немногие исключения
(единицы SVG в графиках, код приглашения, пропорции фирменного знака)
подписаны комментарием на месте.

| Шкала | Токены | Значения |
|---|---|---|
| Текст | `--fs-caption / small / ui / body / lead / h3 / h3-lg / title / h2 / display` | 12 / 13 / 14 / 15 / 17 / 20 / 24 / 28 px, заголовки витрины — `clamp()` 28–42 и 32–56 |
| Насыщенность | `--fw-regular / medium / semibold / bold / heavy` | 400 / 500 / 600 / 700 / 800 |
| Скругления | `--radius-sm / radius / radius-lg / radius-xl / radius-pill` | 8 / 12 / 20 / 24 / 999 — поля и кнопки, карточки панелей, карточки витрины, крупные панели, «таблетки» |
| Отступы | `--space-1 … --space-9` | 4 / 8 / 12 / 16 / 20 / 24 / 32 / 48 / 64 |
| Движение | `--dur-fast / dur / ease` | .14s наведение, .25s переход, одна кривая на всё |

Цвета — семантические: `--bg`, `--surface`, `--surface-2`, `--text`,
`--text-soft`, `--text-faint`, `--accent`, `--ok`, `--warn`, `--danger`,
`--info`, `--border`. Панели сотрудников переключают их светлой и тёмной
темой, витрина переопределяет на `body.landing` своим неоном. У витрины
сверх того:

| Токен | Для чего |
|---|---|
| `--tint`, `--tint-strong` | подложки чипов, кнопок, приглушённых меток |
| `--line`, `--line-mid`, `--line-strong`, `--line-bright` | границы по силе: разделитель → граница кнопки → кант выделенной карточки |
| `--glow-faint`, `--neon-dim`, `--glow`, `--glow-strong` | свечение неона по силе |
| `--deep-haze`, `--deep-glow` | дальний синий ореол |
| `--glass-top/bottom`, `--glass-accent-top/bottom` | стекло карточки и выделенной карточки |
| `--bar`, `--bar-clear` | шапка, верхняя строка, подвал |
| `--section-gap`, `--pad-card`, `--pad-card-sm`, `--pad-panel`, `--gap-grid` | ритм страницы; на узком экране меняются только эти переменные |

До приведения в порядок на витрине было 27 размеров шрифта, 9 скруглений,
18 плотностей одного голубого для линий и 14 — для свечения; разницу между
соседними глаз не видел, а объяснить её не мог никто.

**Компоненты** (`app.css`): `.btn` (варианты `-primary`, `-ghost`, `-danger`,
`-ok`, на витрине ещё `-outline` и `-on-dark`; размеры `-sm`, `-lg`, `-block`), поля ввода и `.field`,
`.card`, `.stat`, `.badge-*`, таблица, `.tabs`, `.toast`, модальное окно
`App.ask()` (`role="dialog"`), `.empty`. Витрина добавляет `.glass` (стекло)
и выделенное стекло `.tile-accent` / `.way-primary` — одно правило на оба.

Правила, которые проверены и держатся:

- Нажимаемое на витрине — не ниже 40 px, телефон в верхней строке — 44 px.
- `--text-faint` на тёмной витрине — не темнее `#7d92b3`: мелкие подписи на
  стеклянных карточках иначе проседают ниже 4,5:1.
- Первый экран без анимации появления: предложение и кнопки видны в первом
  кадре. Анимация — только у блоков ниже.
- Знак в шапке прячется, пока на экране вывеска первого экрана, — два знака
  подряд спорили за первый взгляд.
- На экране уже 760 px меню скрыто: разделы и так идут лентой, а прокрутка
  меню вбок читалась как обрезанная вёрстка.

### Лендинг

Витрина, а не приложение: **работает без JavaScript**. Масла и адреса рендерятся
на сервере из тех же таблиц, что отдаёт API, — витрина не разъедется с тем, что
клиент увидит в приложении.

Страница одета по фирменному знаку «Мой Сервис»: почти чёрный фон с синим
подтоном, контуры неоновой трубкой, «хромированные» надписи. Поэтому **лендинг
всегда тёмный и переключателя темы на нём нет**: неон на белом фоне не светится,
а светлый вариант витрины читался бы как другая компания. Светлая и тёмная темы
остались там, где ими действительно пользуются, — в панелях сотрудников.

Структура осталась прежней (утилитарная полоса, первый экран во всю ширину,
полоса цифр, разноразмерные плитки, масла, два пути записи, адреса карточками,
блок приложения, FAQ на `<details>`, полоса с телефоном), изменились подача и
материал: вместо плоских светлых карточек — «стекло» с волосяной градиентной
рамкой, вместо оранжевого акцента — синий неон логотипа.

#### Фактура фона

Фон витрины — не плоская заливка, а тёмно-синяя поверхность с крупной
облачной фактурой, как на фирменной картинке. Сделана без единого файла:
`feTurbulence` внутри `data:`-URI в `landing.css`.

Почему не картинкой: текстура такого размера весила бы сотни килобайт,
тянулась бы отдельным запросом и на широком мониторе повторялась бы видимым
швом. `stitchTiles='stitch'` сшивает плитку бесшовно, размер задаёт
`background-size`.

Параметры подобраны не на глаз, а замером. Пиксели фирменной картинки
разобраны через canvas: средний тон её фона — `#030b14` (заметно синее
прежнего `#04070e`), разброс зерна около единицы из 255, и он сильнее в
синем канале, чем в красном. Отсюда два решения:

- **Базовый цвет `--void` взят ровно с картинки.** Это и даёт основное
  сходство — фактура вторична, цвет первичен.
- **Режим наложения `soft-light`, а не обычный.** Серый шум обычным
  наложением обесцвечивает фон в графит: на первых пробах синева пропадала
  совсем. `soft-light` меняет светлоту, но сохраняет тон.

Частота `0.5` при четырёх октавах даёт именно облачность, а не мелкое
зерно: на образце фактура крупная, пиксельный шум на неё не похож.

Фактура только на лендинге. В панелях сотрудников её нет намеренно: там
светлая и тёмная темы и рабочие таблицы, которым фон должен не мешать.

#### Цен на сайте нет

Решение заказчика: стоимость называют по телефону и мастер на месте.
Флаг `COMPANY_SHOW_PRICES`, который раньше включал таблицу цен, удалён
вместе с таблицей — лишняя переменная в `.env` однажды включилась бы по
ошибке. Секция «Расходные материалы» осталась карточками: бренд,
название, вязкость, тип, объём. Клиенту важно увидеть, что нужное ему
есть.

Остатков на складе на витрине тоже нет: сколько масла лежит на точке —
внутренняя информация. Слово «канистра» в обращении к клиенту не
используется — ни на сайте, ни в приложении.

#### Фирменный знак

`templates/web/_logo.html` — силуэт машины неоновой трубкой и надпись поверх
него. Нарисован вектором, а не картинкой: знак стоит в шапке, на первом экране
и в подвале, растровый файл пришлось бы возить в трёх размерах.

- Свечение даётся CSS-фильтром `drop-shadow` в три слоя, а не SVG-фильтром: тот
  пришлось бы объявлять в `defs`, а знак на странице встречается трижды —
  получились бы дубли `id`.
- Размер задаётся одной переменной `--logo-w`, от неё считается и надпись, —
  пропорции лока не зависят от того, где он стоит.
- Крыша и порог выходят из одной точки слева: этот клин и читается как нос
  машины, без схождения остаются просто две дуги.
- Длину каждой линии измеряет `landing.js` и кладёт в переменную `--len`:
  прошитая в CSS константа обрезала бы чужой рисунок или оставляла его мигать.
- Слова в знаке заданы текстом в шаблоне, а не берутся из `COMPANY_NAME`: это
  рисунок, а не подпись. Название компании в `.env` должно ему соответствовать —
  в подвале и в `<title>` выводится именно оно.

#### Как подставить свой рисунок знака

Меняется один блок в `templates/web/_logo.html` — `<g class="logo-lines">`.
Ни CSS, ни JS трогать не нужно: длину каждой линии `landing.js` измеряет сам
(`getTotalLength`) и кладёт в переменную `--len`, а блик делает копией пути.
Поэтому анимация повторится на любой геометрии, ничего подгонять руками не
придётся.

**Рисунок бывает двух видов, и от этого зависит анимация.**

*Заливка* — линия задана границами самой ленты, замкнутым контуром. Так
нарисован текущий знак: группа помечена `logo-lines-solid`, атрибут
`fill="none"` убран. Толщина получается переменной, с сужением к носу и
корме, — у ровной обводки такого не бывает, и для неона это выглядит
лучше. Плата: прочерчивания нет, знак загорается разом. Мигание «розжига»,
свечение и бегущий блик работают.

*Осевые линии* — каждая линия отдельный `<path>` с обводкой. Тогда знак
прочерчивается от начала к концу, линия за линией. Для этого группе нужен
`fill="none"` и никакого `logo-lines-solid`.

**Требования к осевому варианту.** Без них прочерчивание не заработает:

1. **Линии должны быть обводкой (`stroke`), а не заливкой (`fill`).** Знак
   загорается тем, что обводка прочерчивается от начала к концу; у залитой
   фигуры чертить нечего. В Illustrator это значит не применять
   Object → Expand, в Figma — оставить Stroke и не делать Outline stroke.
2. **Каждая линия — отдельный `<path>`.** `<line>`, `<polyline>`, `<circle>`,
   `<rect>` тоже подойдут. А вот `<g>` с вложенными фигурами анимируется
   целиком, как один объект.
3. **Каждому пути нужен `class="logo-line"`.**
4. **Ни `fill`, ни `stroke`, ни `filter` в самом SVG прописывать не надо** —
   цвет и свечение приходят из CSS. Экспорт с инлайновыми стилями
   («Presentation attributes» в Illustrator) их перебьёт: такие атрибуты
   нужно удалить.
5. **Порядок путей в разметке = порядок, в котором они загораются.**
   Задержки стоят в `landing.css` на `.logo-line:nth-child(1..6)`.
6. **`viewBox` подставьте свой** — пропорции знака берутся из него. Атрибуты
   `width` и `height` у `<svg>` не нужны, размер задаёт CSS.
7. **Одному пути добавьте `data-spark`** — самому длинному и заметному,
   обычно линии крыши. По нему раз в семь секунд пробегает блик-отражение.

**Порядок действий:**

1. Нарисовать знак линиями в Illustrator, Figma, Inkscape — где удобно.
2. Экспортировать в SVG. В Figma: Export → SVG, галочки «Include id
   attribute» и «Outline text» снять. В Illustrator: File → Export →
   SVG, Styling → «Internal CSS», Object IDs → «Minimal».
3. Открыть файл текстовым редактором, забрать оттуда `viewBox` и сами
   `<path d="…">`.
4. В `_logo.html` заменить содержимое `<g class="logo-lines">` своими
   путями, каждому дописать `class="logo-line"`, одному — `data-spark`.
5. Толщину линий править в `landing.css`: либо общую у `.logo-line`, либо
   отдельным классом конкретному пути.

**Проверить, что получилось**, удобнее всего в консоли браузера на главной:

```js
[...document.querySelectorAll('.logo-line')]
  .map(l => [l.getAttribute('class'), l.style.getPropertyValue('--len')])
```

У каждой линии должно стоять число — измеренная длина. Пусто означает, что
фигура не поддерживает `getTotalLength` (скорее всего это `<g>`), и такую
линию нужно разбить на отдельные пути.

Для варианта с заливкой из этих требований обязателен только пункт 6
(`viewBox`) и пункт 7 (`data-spark`): всё остальное относится к обводке.

**Надпись** («Мой Сервис», одной строкой поперёк кузова) набрана текстом
поверх рисунка и красится хромовым градиентом в CSS, а не нарисована в SVG:
так она берётся из одной строки шаблона и не требует перерисовки кривых при
смене названия. Если буквы уже нарисованы внутри SVG, удалите из
`_logo.html` блок `<span class="logo-word">`, иначе надпись задвоится.

Два решения в надписи:

- **Размеры считаются от `--logo-w`, а не в процентах от высоты бокса.**
  Высота знака зависит от пропорций рисунка, и при его замене проценты
  поехали бы вместе с ней.
- **Строка растянута по горизонтали** (`scaleX(1.1)`): на образце гарнитура
  заметно шире Arial Black. Тянуть ради одного слова веб-шрифт — лишний
  запрос, вес и мигание при загрузке, а лёгкое искажение на таком кегле
  незаметно.

**При смене названия подбирайте кегль и посадку заново.** Оба заданы долей
от `--logo-w` (сейчас `.078` и `.137`). Слово другой длины либо вылезет за
габарит кузова, либо потеряется на нём, а строка не должна наезжать на
линии машины: надпись стоит *под* линией борта, а не поперёк неё. Проверить
пересечения можно в консоли браузера — `isPointInFill()` по сетке точек
внутри текстового бокса:

```js
const L = document.querySelector('.logo-hero');
const svg = L.querySelector('.logo-car');
const path = L.querySelector('.logo-line-body');
const r = document.createRange();
r.selectNodeContents(L.querySelector('.logo-word-main'));
const t = r.getBoundingClientRect();
const m = svg.getScreenCTM().inverse();
let hits = 0;
for (let i = 0; i <= 80; i++) for (let j = 0; j <= 24; j++) {
  const p = svg.createSVGPoint();
  p.x = t.left + t.width * i / 80;
  p.y = t.top + t.height * j / 24;
  if (path.isPointInFill(p.matrixTransform(m))) hits++;
}
hits;   // попадания в верхней полосе — это межстрочный отступ, не буквы
```

Заодно проверьте, что знак по-прежнему влезает в шапку: её высоту задаёт
`--header-h` на `.landing`.

#### Движение

Анимация на странице делает ровно три вещи и ничего сверх:

1. **Бренд.** При открытии трубка «схватывается» с неровным миганием —
   проценты в `@keyframes neon-ignite` намеренно неравномерные, ровный fade
   выдал бы обычное появление картинки. Дальше раз в семь секунд по кузову
   пробегает короткий блик; большую часть цикла он стоит за краем кадра,
   витрина не должна мигать. Прочерчивание линий у текущего знака не
   работает — он нарисован заливкой, подробности выше.
2. **Появление блоков.** Один раз, на 14 px, без возврата при обратной
   прокрутке: повторный выезд читается как баг, а не как оформление. Соседи в
   группе идут с задержкой по индексу, но не больше шести шагов — дальше выход
   блока превращается в ожидание. Кривая одна на весь лендинг
   (`--ease: cubic-bezier(.22, 1, .36, 1)`): разнобой в ускорениях и делает
   анимацию самодельной.
3. **Реакция на курсор.** Блик под указателем на стеклянных карточках (это
   отражение, поэтому он следует за мышью, а не просто «подсвечивает»),
   зажигание строки прайса и подчёркивание в меню, разъезжающееся из центра.

Мокап приложения на первом экране — не картинка, а короткий показ сценария
записи: шаги загораются по очереди, выбирается время, утекает таймер брони, в
конце нажимается подтверждение. Цикл 12 секунд, целиком на CSS — так одна строка
`prefers-reduced-motion` выключает его вместе со всем остальным, а JS только
ставит его на паузу, когда мокап уехал с экрана.

Правила, которые держат этот слой:

- **Страница обязана работать без `landing.js`.** Он ничего не рендерит, только
  доигрывает отрисованное сервером. Блоки прячутся классом `has-js`, который
  ставится инлайновым скриптом в `<head>` до отрисовки: нет JS — нет класса, всё
  видно. Если что-то в скрипте упало, `catch` показывает все блоки разом.
- **Обработчиков прокрутки и движения мыши ровно по одному**, и оба сведены в
  `requestAnimationFrame`. Границы карточки читаются только при смене цели:
  `getBoundingClientRect` на каждое движение мыши заставляет браузер
  пересчитывать раскладку.
- **Счётчики на первом экране докручиваются один раз** по `easeOutExpo` и только
  когда доехали до экрана. Не сработал `IntersectionObserver` — в разметке уже
  лежит готовое число с сервера.
- **`prefers-reduced-motion` выключает всё**, но неон при этом горит, а не
  остаётся недорисованным.

Записи на сайте нет намеренно: клиент записывается в приложении или по телефону,
и веб-форма дублировала бы сценарий, за которым нужно следить в двух местах.

Контакты и ссылки на магазины лежат в `.env` (`settings.COMPANY`): телефон и
ссылки меняет не программист, и правка не должна требовать ни редактирования
кода, ни пересборки образа. Пока ссылка пустая, кнопка магазина показывается
неактивной с пометкой «скоро» — а не ведёт в никуда.

### Панели сотрудников

```
static/web/css/app.css     дизайн-система: переменные, светлая и тёмная темы
static/web/css/landing.css стили лендинга — грузятся только на главной
static/web/js/core.js      запросы к API, обновление токена, тосты, тема, формат
static/web/js/landing.js   движение на лендинге — грузится только на главной
static/web/js/staff.js     смена: реальное время, фильтры, действия по записям
static/web/js/metrics.js   метрики администратора и графики в SVG
```

- **Список живёт в реальном времени.** Канал `ws/master/` присылает сигнал, панель
  перечитывает текущую выборку. Опрос раз в 20 секунд остаётся, но включается
  только когда канал недоступен: реальное время не должно зависеть от того,
  разрешён ли WebSocket в сети клиента. Состояние связи видно в шапке смены.
- **«Записать клиента»** — окно над списком: телефон (есть в базе —
  имя подставится, а машины клиента появятся кнопками), машина, адрес, масло из наличия и время
  сеткой кнопок; открывается на первом дне, где у точки есть свободное
  время, после записи список переключается на её день.
- **Время показывается в часовом поясе точки**, а не браузера: `local_time`
  приходит с сервера. Мастер в другом регионе увидит то же, что и клиент.
- **Токены клиента и сотрудника лежат под разными ключами `localStorage`.**
  За одним браузером сидит один человек, но роли у него разные.
- **`access` обновляется молча.** Он живёт час; при `401` `core.js` меняет его по
  `refresh` и повторяет запрос — вкладка, открытая с утра, не начинает сыпать
  ошибками.
- **Заход не на свою панель не рвёт сессию.** Мастер на `/admin-panel/` видит
  объяснение и ссылку на своё рабочее место, а не разлогин.
- **Графики нарисованы вручную в SVG.** Данных немного, зато диаграммы сами
  подхватывают цвета темы из CSS-переменных и не тянут стороннюю библиотеку.
- **Тема переключается кнопкой и запоминается**, а по умолчанию берётся из
  системной настройки (`prefers-color-scheme`).

### Раздача статики

В разработке HTTP-приложение обёрнуто в `ASGIStaticFilesHandler` (`config/asgi.py`).
Daphne — не `runserver`: сам он статику не отдаёт, а `staticfiles` подменяет
обработчик только в команде `runserver`, поэтому без обёртки CSS и JS отдавались
бы как `404`. При `DEBUG=False` обёртки нет — в проде статику раздаёт nginx
перед daphne.

## Мобильное приложение

Android-приложение (`mobile/android`, Java) с версии 2.0 — **оболочка
(WebView) над тем же веб-приложением `/app/`**, что ставится на iPhone.
Экраны клиента пишутся один раз и на обеих платформах совпадают по
построению; решение заказчика, октябрь 2026.

| Что | Значение |
|---|---|
| Минимальная версия | Android 7.0 (API 24), собирается под API 35 |
| Экраны | веб-приложение `/app/` — то же, что на iPhone |
| Нативный слой | мост `window.MoiServisNative`: токены в Keystore, «Поделиться», буфер обмена, отступы под системные панели; App Links и Install Referrer для приглашений; камера для сканера QR; «Назад»; экран «нет связи» |
| Зависимости | AndroidX (appcompat, splashscreen, security-crypto) и Install Referrer |

Веб-приложение узнаёт оболочку по мосту (`isAndroidShell()` в
`app/lib.js`): проверка «только iPhone с главного экрана» для неё не
действует, токены уходят в Keystore вместо localStorage, «Назад» сначала
закрывает окна и возвращает на первую вкладку.

**Порядок выкатки:** сначала сервер (веб-приложение должно узнавать
оболочку), потом новая сборка. Иначе оболочка 2.0 на старом сервере покажет
«Для Android — приложение из Google Play».

Подробности — устройство оболочки, безопасность моста, сборка, подпись и
Play Console — в [`mobile/android/README.md`](mobile/android/README.md).

## Известные ограничения и подводные камни

1. **Кириллица в пути ломает `docker compose build`** без имени сервиса. Обход —
   `docker compose build api` (в `Makefile` уже так). Подробности — в разделе
   «Быстрый старт».
2. **`OTP_DEBUG_EXPOSE_CODE=True` возвращает код входа прямо в ответе API.** Удобно
   в разработке; в прод-настройках значение принудительно `False`, переключить
   его из `.env` нельзя.
3. **График «через полночь» не поддерживается** осознанно: если `closes_at <= opens_at`,
   слоты на день не строятся. Для круглосуточной точки ставьте `00:00`–`23:30`.
4. **Push-уведомлений нет** — только SMS. Модель `Notification` уже имеет поле
   `channel` со значением `push`, но отправка не реализована.
5. **Ссылка-приглашение открывается приложением только в релизной сборке.**
   Android App Links проверяют подпись через `/.well-known/assetlinks.json`,
   а у отладочной сборки она другая — ссылка откроется в браузере, на
   странице с кодом. Пока `ANDROID_CERT_FINGERPRINTS` пуст, этот файл
   отдаёт 404 намеренно: пустой или выдуманный Android считает провалом
   проверки, и отлаживать это потом очень неприятно.
6. **Записи на сайте нет** — это осознанное решение: клиент записывается в
   приложении или по телефону. Сценарий записи полностью живёт в API.
7. **Онлайн-оплаты нет.** Цены фиксируются в записи, расчёт на месте.
8. **Дерева рефералки и журнала выплат в панели администратора нет** — только
   Django-админка. Списание баллов при расчёте работает (окно «Расчёт» у мастера).
9. **Один сервис — замена масла.** Модели `Oil`/`OilStock` заточены под канистры;
   для второй услуги понадобится ввести сущность «услуга».
10. **Мастер не привязан к записи автоматически** — поле `master` заполняется, когда
   он берёт запись в работу.
11. **Отмена клиентом возможна только из статуса `pending`.** Если мастер уже начал
   работу, отменить нельзя.
12. **Access-токен WebSocket едет в адресе** (`/ws/booking/?token=…`): браузер не
   умеет слать заголовки при подключении. Из access-лога nginx строка запроса
   убрана (`log_format ws_no_args` в `deploy/nginx.conf.example`), но сам
   контракт остаётся: токен виден в истории браузера и в любом промежуточном
   прокси, который логирует URL. Лечится одноразовым тикетом вместо JWT — и
   ломает совместимость с уже собранным Android-клиентом.
13. **Телефоны в логах маскируются** (`+7900***4567`), но коды броней и
   идентификаторы записей пишутся как есть. Провайдер `console` печатает SMS
   вместе с кодом входа — он для разработки, и `security_audit` считает его
   на проде провалом.

## Деплой на сервер

Базовый `docker-compose.yml` рассчитан на разработку: он пробрасывает наружу
порты PostgreSQL, Redis и daphne. На машине с публичным адресом так нельзя —
Redis без пароля находят автоматические сканеры за минуты. Поэтому на проде
compose запускается с надстройкой `docker-compose.prod.yml`, которая эти порты
убирает, собирает образ без dev-зависимостей и монтирует статику в каталог
хоста для nginx.

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
```

### Порядок развёртывания

1. **Docker и nginx на сервере.** Docker — из официального репозитория, а не
   `docker.io` из Ubuntu: надстройке нужен Compose не ниже 2.24 (теги `!reset`),
   а в системных репозиториях он бывает старее.
   ```bash
   curl -fsSL https://get.docker.com | sh
   apt update && apt install -y git nginx certbot python3-certbot-nginx
   docker compose version   # должно быть 2.24 или выше
   ```
2. **Клонировать в `/opt/auto_service`** (этот путь прописан в примере конфига
   nginx) и создать каталоги статики:
   ```bash
   git clone https://github.com/Nikita885/auto_service.git /opt/auto_service
   cd /opt/auto_service && mkdir -p static media && chown -R 1000:1000 static media
   ```
   `1000` — uid пользователя `appuser` внутри контейнера. Без этого
   `collectstatic` упрётся в права хоста.
3. **Заполнить `.env`** по чек-листу ниже. Ключ генерируется так:
   ```bash
   python3 -c "import secrets; print(secrets.token_urlsafe(50))"
   ```
4. **Поднять контейнеры** командой выше.
5. **Настроить nginx**: скопировать [`deploy/nginx.conf.example`](deploy/nginx.conf.example)
   в `/etc/nginx/sites-available/autoservice`, слинковать в `sites-enabled`,
   проверить `nginx -t` и перезагрузить.
6. **Выпустить сертификат** — бесплатный Let's Encrypt, продлевается сам.
   Перечислять нужно все имена, включая те, что только редиректят: сертификат
   предъявляется до редиректа, и без имени в нём браузер покажет ошибку
   безопасности вместо перехода.
   ```bash
   certbot --nginx -d <домен> -d www.<домен> -d <домен-2> -d www.<домен-2>
   ```
7. **Создать администратора**, раз демо-данных на проде нет:
   ```bash
   docker compose -f docker-compose.yml -f docker-compose.prod.yml exec api \
       python manage.py createsuperuser
   ```
8. **Поставить бэкапы в cron** — см. «Бэкапы PostgreSQL» ниже. До этого шага
   сервер нельзя считать запущенным: отказ диска означает потерю всей
   клиентской базы и истории записей.
9. **Прогнать чек-лист** — `manage.py security_audit`, см. «Чек-лист перед
   продом». Команда должна закончиться без единого `ПРОВАЛ`.

### Обновление уже развёрнутого сервера

```bash
cd /opt/auto_service
git pull
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
```

Почему именно перезапуск контейнера, а не просто `git pull`:

- **Шаблоны кешируются в памяти процесса.** При `DEBUG=False` Django сам
  оборачивает загрузчики в `cached.Loader`. Прод-надстройка монтирует код с
  хоста (`.:/app`), то есть новый HTML лежит на месте сразу — но daphne
  продолжает отдавать разобранный старый, пока его не перезапустят.
- **`collectstatic` запускается в `entrypoint.sh` при старте `api`.** Пока
  контейнер не перезапущен, в `static/` лежит прошлая сборка CSS и JS.
- `--build` нужен, только если менялись зависимости; в остальных случаях
  достаточно `restart api`, но лишним он не будет.

Миграции применяются тем же entrypoint автоматически. Изменения, которые
трогают только вёрстку и стили, миграций не требуют вовсе.

**Конфиг nginx после `git pull` сам не обновится.** На сервере он лежит в
`/etc/nginx/sites-available/`, и certbot дописал в него ssl-секции — просто
скопировать поверх новый пример значит потерять HTTPS. Изменения из
`deploy/nginx.conf.example` переносятся руками, после чего `nginx -t` и
`systemctl reload nginx`.

**После правки `.env` контейнер тоже надо перезапустить** — переменные
окружения читаются один раз при старте. `.env` в репозиторий не входит, так что
новые ключи после `git pull` не появятся сами: сверяйтесь с `.env.example`.

### Бэкапы PostgreSQL

Снимок снимает [`deploy/backup.sh`](deploy/backup.sh) — на **хосте**, по cron,
не внутри контейнера:

```bash
crontab -e
10 3 * * * /opt/auto_service/deploy/backup.sh >> /var/log/autoservice-backup.log 2>&1
```

Дамп снимается тем же образом, что крутит базу (`docker compose exec db
pg_dump`): на хосте клиента postgresql может не быть вовсе, а версии клиента
и сервера обязаны совпадать по мажору. Формат custom (`-Fc`) сжат, даёт
выборочное восстановление и не зависит от порядка таблиц.

Файл сначала пишется под именем `*.part` и переименовывается только после
проверки сигнатуры `PGDMP` в первых байтах: оборванный дамп не должен
выглядеть готовым снимком, иначе ротация однажды удалит последний целый.

Настройки — в `.env`:

```bash
BACKUP_DIR=backups          # относительно корня проекта
BACKUP_KEEP_DAYS=14         # ротация по времени, а не по числу файлов
BACKUP_MAX_AGE_HOURS=36     # старше — security_audit считает бэкапы протухшими
BACKUP_REMOTE=              # цель rsync за пределами сервера
```

**`BACKUP_REMOTE` — не опция.** Снимки лежат на том же диске, что и база:
от случайного `DROP` и от порчи данных это спасает, от отказа диска — нет,
а именно отказ диска и есть тот сценарий, ради которого бэкапы делают.
Годится любая цель rsync: `backup@storage.example.com:/srv/autoservice`.

Восстановление:

```bash
# в существующую базу, с заменой объектов
docker compose -f docker-compose.yml -f docker-compose.prod.yml exec -T db \
    pg_restore -U autoservice -d autoservice --clean --if-exists \
    < backups/autoservice-20260921-030000.dump
```

Перед восстановлением остановите `api`, `worker` и `beat` — иначе они будут
писать в базу, которую в этот момент переливают.

**Снимок, из которого ни разу не восстанавливались, бэкапом не является.**
Проверять стоит на отдельной базе, не трогая рабочую:

```bash
docker compose … exec -T db psql -U autoservice -d postgres -c "CREATE DATABASE restore_probe;"
docker compose … exec -T db pg_restore -U autoservice -d restore_probe < backups/<файл>.dump
docker compose … exec -T db psql -U autoservice -d restore_probe -c "select count(*) from booking_booking;"
docker compose … exec -T db psql -U autoservice -d postgres -c "DROP DATABASE restore_probe;"
```

Свежесть снимков проверяет `manage.py security_audit`: прод монтирует каталог
проекта в контейнер, поэтому команда видит те же файлы, что и cron на хосте.

### Почему имена файлов статики с хешем

В проде `STORAGES` подменяет хранилище на хеширующее: `{% static %}` отдаёт
`landing.a1b2c3d4.css` вместо `landing.css`, и nginx раздаёт `/static/` с
`Cache-Control: immutable` на год.

Причина простая. HTML браузер не кеширует — его каждый раз рендерит Django. CSS
по неизменному адресу он кеширует надолго. Значит после выкатки нового
оформления вернувшийся посетитель получил бы **новую разметку со старыми
стилями** — то есть сломанную страницу, и чинилась бы она сама только когда
истечёт срок жизни кеша. Задним числом чужой браузерный кеш не сбрасывается
ничем, кроме смены адреса файла.

Хранилище намеренно «прощающее» (`manifest_strict = False`,
`apps/common/staticfiles.py`): `collectstatic` в entrypoint запускается с
`|| true`, и если он однажды упадёт, файл без записи в манифесте отдастся по
имени без хеша, а не уронит страницу пятисоткой.

### Смена основного домена

Так переезжали с `moiservis.pro` на `moi-servis.ru` (сентябрь 2026).
Домены прошлого бренда («Экспресс Замена») отдают `301` на новый с
сохранением пути. **Сам `moiservis.pro` передан другому проекту** на этом
же сервере и в нашем конфиге nginx не упоминается вовсе: одно имя в двух
конфигах nginx отдаёт одному из них наугад.

**Что меняется в коде:** `COMPANY_SITE_URL` по умолчанию
(`config/settings/base.py`, `.env.example`), `deploy/nginx.conf.example`,
релизные `API_BASE_URL`/`WS_BASE_URL` в `mobile/android/app/build.gradle`
(только основной домен: OkHttp с JWT за `301` не пойдёт) и `invite_host`
в `strings.xml`.

**Что меняется на сервере:** `.env` (`ALLOWED_HOSTS`,
`CSRF_TRUSTED_ORIGINS`, `COMPANY_SITE_URL`), конфиг nginx, сертификат.
`security_audit` проверяет, что адрес из `COMPANY_SITE_URL` входит в
`ALLOWED_HOSTS` и `CSRF_TRUSTED_ORIGINS`: поправить одно и забыть другое —
самая вероятная ошибка переезда, и стоит она каждой разосланной ссылки.

**Что происходит со старым:**

- **Ссылки и QR-коды приглашений** со старым доменом теперь в руках
  проекта, которому передан `moiservis.pro`: пока он отдаёт `301` с
  `/i/<код>` на `moi-servis.ru`, они работают. Сканер в приложении читает
  код из любой такой ссылки — код не привязан к домену.
- **Android App Links** — только на `moi-servis.ru`: проверка идёт по
  `/.well-known/assetlinks.json` и за редиректами не ходит, а чужой домен
  нам его не отдаст.
- **Веб-приложение на главном экране iPhone** привязано к адресу, с
  которого его установили, и хранит вход в хранилище этого адреса.
  Установленное со старого домена после `301` уйдёт в Safari без входа —
  его нужно удалить с экрана «Домой» и поставить заново с нового адреса
  (вход по SMS заново, записи и баллы на месте — они на сервере).
- **Отладочные APK**, собранные с адресом старого домена, после переезда
  не работают (тот же `301` для OkHttp) — нужна новая сборка.
- **Поисковики** склеят адреса по `301` сами.

### Кириллический домен

Если доменов два — латинский и кириллический, — основным стоит делать
латинский, а кириллический редиректить на него (так сделано в примере конфига
nginx). Иначе punycode придётся тащить в `ALLOWED_HOSTS`, в сборку Android-
приложения и в каждую внешнюю интеграцию, и каждое из этих мест — отдельный
шанс ошибиться в строке, которую невозможно прочитать глазами.

Домен вида `экспрес-замена.рф` в заголовке `Host` приходит в **punycode**
(`xn----8sbarcksuknlkd6n.xn--p1ai`), и certbot работает только с этой формой.
В `ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS`, `CORS_ALLOWED_ORIGINS` и
`server_name` нужен именно punycode — с кириллицей в `ALLOWED_HOSTS` Django
ответит `400 Bad Request` на каждый запрос. Перевести домен можно так:

```bash
python3 -c "print('экспрес-замена.рф'.encode('idna').decode())"
```

### Что ещё делает конфиг nginx

- **Строка запроса `/ws/` не пишется в access.log** (`log_format
  ws_no_args`). Браузер не умеет слать заголовки при открытии WebSocket,
  поэтому access-токен едет в адресе: `/ws/booking/?token=<JWT>`. В обычном
  combined-формате он лежал бы в файле, пока логи не ротируются, — готовый
  вход в чужой аккаунт для всякого, кто дотянулся до логов или до их
  выгрузки.
- **Лимит на форму входа в админку** — `limit_req` 10 запросов в минуту с
  адреса на `= /admin/login/`. Это единственная форма на сайте, которую
  защищает только пароль: эндпоинты входа в API лимитирует сам DRF, а за
  админкой лежат телефоны и госномера всей клиентской базы. Лимит висит
  именно на форме, а не на всём `/admin/`, иначе в тот же счётчик упёрлась
  бы обычная работа администратора со справочниками.

### Почему в nginx нужен `X-Forwarded-Proto`

В прод-настройках включён `SECURE_SSL_REDIRECT`, а схему запроса Django берёт
из `SECURE_PROXY_SSL_HEADER`. Если nginx не передаст этот заголовок, Django
сочтёт запрос пришедшим по HTTP и отправит редирект на HTTPS — который nginx
снова проксирует на тот же обработчик. Получится бесконечная петля редиректов.
В примере конфига заголовок проставлен во всех секциях.

## Чек-лист перед продом

Проверяется не глазами, а командой — **на сервере, внутри контейнера**, чтобы
видеть те настройки, с которыми реально работает сайт, а не те, что написаны
в файле:

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml \
    exec api python manage.py security_audit
```

Команда печатает по строке на пункт и возвращает код 1, если что-то
провалено, — её можно повесить в cron и не читать вывод глазами:

```
[   OK   ] DEBUG — выключен
[ ПРОВАЛ ] SMS_PROVIDER — console — сообщения не уходят, а печатаются в лог…
[ВНИМАНИЕ] SENTRY_DSN — не задан — ошибки прода видны только в логах
```

`--strict` считает провалом и предупреждения.

Что она проверяет: `DJANGO_SETTINGS_MODULE`, `DEBUG`, `SECRET_KEY`,
`OTP_DEBUG_EXPOSE_CODE`, `ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS`, CORS,
`SECURE_*` и secure-cookie, `NUM_PROXIES`, лимиты throttling, настройки SMS,
пароль PostgreSQL, `BOOTSTRAP_DEMO`, демо-учётки (именно «пускает ли
известный всем пароль», а не «существует ли пользователь»), свежесть бэкапов
и `SENTRY_DSN`.

Часть пунктов проверить кодом нельзя — они остаются за человеком:

- [ ] HTTPS-терминация перед daphne настроена и сертификат покрывает **все**
      имена, включая те, что только редиректят
- [ ] `OTP_DEBUG_PHONES` пуст — временная заглушка с кодом в ответе API убрана
- [ ] `SMS_SENDER` — зарегистрированный буквенный отправитель прошёл модерацию
      (https://sms.ru/?panel=senders), на счету есть деньги;
      проверить `manage.py send_test_sms +7…`
- [ ] `SMS_ENABLED_KINDS` — выключено то, за что платить не хочется
- [ ] `COMPANY_NAME` и остальные `COMPANY_*` — реальные: их видят в заголовке
      вкладки, в шапке панелей и в подвале лендинга
- [ ] `deploy/backup.sh` стоит в cron, `BACKUP_REMOTE` ведёт за пределы
      сервера, и **восстановление из снимка хотя бы раз проверено**
- [ ] телефоны и госномера — персональные данные (152-ФЗ): нужна политика
      обработки, согласие при регистрации, хранение на серверах в РФ

### Что нельзя выключить настройкой

Две вещи прод не отдаёт на откуп `.env`, потому что цена опечатки в нём —
открытая система, а не замечание в отчёте:

- **`OTP_DEBUG_EXPOSE_CODE` в проде всегда `False`.** Переменная читается, но
  `settings/prod.py` перетирает результат. Иначе одна строка в `.env`
  возвращает код входа прямо в ответе API — то есть вход в любой аккаунт по
  одному лишь номеру телефона.

  Исключение сделано ровно одно и намеренно: `OTP_DEBUG_PHONES`
  перечисляет номера, которым код всё же возвращается в ответе.
  Это временная заглушка на то время, пока у SMS-шлюза не согласован
  буквенный отправитель: без неё войти в приложение на живом сервере
  нельзя вообще. **Каждый номер в списке — открытая дверь в этот
  аккаунт**, поэтому `security_audit` считает непустой список провалом, а
  каждое срабатывание пишется в лог предупреждением. Убрать сразу после
  запуска SMS.
- **`SECRET_KEY` из репозитория не даёт приложению запуститься вовсе.** Этим
  ключом подписываются JWT (`SIMPLE_JWT["SIGNING_KEY"]`), и публично известное
  значение здесь — это возможность выписать себе токен администратора.
  Прод падает с `ImproperlyConfigured` на старте.
  **Смена ключа разлогинивает всех:** старые access- и refresh-токены
  перестают проверяться, клиенты войдут заново по SMS.

## Что дальше

Ближайшие логичные шаги:

1. **Публикация клиентского приложения** — код готов, нужны ключ подписи и
   заполненная анкета Data Safety. Лендинг ждёт ссылку на магазин
   (`COMPANY_APP_STORE_URL`, `COMPANY_GOOGLE_PLAY_URL`), а ссылки-приглашения —
   отпечаток подписи в `ANDROID_CERT_FINGERPRINTS`, иначе они будут
   открываться в браузере.
2. **Дерево и журнал выплат в панели администратора** — пока только
   Django-админка.
3. **Приложение мастера** — отдельный модуль на том же слое данных:
   `/api/v1/master/…` и канал `ws/master/` готовы полностью.
4. **Push-уведомления** вместо/вместе с SMS (FCM/APNs) — поле `channel` уже есть.
5. **Онлайн-оплата** — эквайринг, статус оплаты в `Booking`.
6. **Автодеплой** — проверки на каждый push уже идут в GitHub Actions;
   осталось выкатывать на сервер по тегу, а не руками.
7. **Расширение услуг** — если появится не только замена масла, ввести модель
   `Service` и связать с ней длительность слота и цену работ.
